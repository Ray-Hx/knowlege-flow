# 04 · 混合检索与 RRF 融合

> 前三篇讲的是同一条路——把检索做得更准。本篇讲另一条路：**不换模型，换融合方式**。让关键词检索和向量检索各跑一遍，再把两份结果合并。
>
> 难点全在「合并」这两个字上。
>
> 涉及代码：`src/main/java/com/ray/knowledgeflow/module/search/service/impl/SearchServiceImpl.java`（674 行）

---

## 一、这个问题为什么难

两个场景，各自暴露一条检索路的盲区。

### 场景 A：向量检索答不好的

用户搜 **`ConcurrentModificationException`**。

这是一个精确的类名。倒排索引一击即中——分词后这个词条只出现在少数几篇笔记里，BM25 的 IDF 会给它极高的权重，排名毫无悬念。

而向量检索会返回一堆讲「并发」「线程安全」「异常处理」的笔记。它们在语义空间里确实离这个查询很近，但用户要的**就是那个类名**，不是「相关话题」。向量检索的模糊性在这里是纯粹的负担。

### 场景 B：关键词检索答不好的

用户搜 **「怎么让搜索既准又能理解意思」**。

用户笔记里那篇正是《混合检索与 RRF 融合》。但两边**一个词都对不上**——笔记里写的是「精确匹配」「语义相似度」「排名融合」，查询里写的是「准」「理解意思」。BM25 找不到任何有效词条，返回空或返回一堆噪声。

向量检索一击即中，因为它比较的是语义而不是字面。

### 两条路互补，但合并时立刻撞墙

结论很清楚：两条路各有盲区，且盲区几乎不重叠，应该都用上。

但**怎么把两份结果合成一份**？最自然的想法是加权求和：

```
最终分数 = α × BM25分数 + β × 余弦相似度
```

这个式子写出来就错了，因为**两个分数不可比**：

| | BM25 分数 | 余弦相似度 |
| :--- | :--- | :--- |
| 取值范围 | 无上界的正实数 | $[-1, 1]$ |
| 决定因素 | 词频、逆文档频率、文档长度、**整个语料的统计特性** | 两个向量的夹角 |
| 同一文档换个查询词 | 可能从 2.1 变成 18.7 | 变化幅度有限 |

BM25 分数**没有稳定的量纲基准**。它依赖 IDF，而 IDF 依赖整个语料——同一篇文档、同一个查询，往语料里再加一万篇笔记，分数就变了。「BM25 得 7.2」这个数字脱离了具体语境毫无意义。

那归一化呢？归一化需要知道分布的上下界，而 BM25 的上界不存在。用当次结果集的 min/max 归一化更糟——同一篇文档在不同查询下归一化出的分数完全不可比，且结果集只有一条时直接退化。

**本篇要解决的就是：两个不可比的分数，怎么合成一个有意义的排序。**

## 二、原理

### 核心思路：扔掉分数，只用排名

这是 RRF（Reciprocal Rank Fusion，倒数排名融合）的全部精髓，一句话说完：

> 「BM25 得 7.2」和「余弦 0.83」不可比，但**「ES 认为它排第 3」和「向量认为它排第 3」是可比的**。

排名是**序数**，无量纲。它天然规避了第一节那个问题——不需要知道分数的范围、分布、基准，只需要知道谁在谁前面。

于是问题从「跨系统分数融合」转化成了「跨系统**排名**融合」。

### 为什么用倒数

需要一个把排名映射成分数的函数，要求随排名递减。最简单的是线性递减，比如 `N - rank`。

**线性递减不合适，因为它对头部和尾部一视同仁。** 用 `N=100` 举例：

| 排名对比 | 线性 `100 - rank` 的差值 | 倒数 `1/rank` 的差值 |
| :--- | :-: | :-: |
| 第 1 名 vs 第 2 名 | 1 | 1 − 0.5 = **0.5** |
| 第 50 名 vs 第 51 名 | 1 | 0.0200 − 0.0196 = **0.0004** |

检索里这两个差距的重要性完全不同：第 1 名和第 2 名的区别，用户一眼就能看到；第 50 名和第 51 名的区别，用户根本翻不到那里。倒数函数天然编码了这个直觉——**头部的排名差异被放大，尾部的被压缩。**

### k 在里面干什么

完整公式是：

$$
\text{score}(d) = \sum_{i} \frac{1}{k + \text{rank}_i(d)}
$$

其中 $i$ 遍历每一路检索，$\text{rank}_i(d)$ 是文档 $d$ 在第 $i$ 路里的排名（从 1 起）。

**如果没有 k**（即 $k=0$），第 1 名得 1 分、第 2 名 0.5 分、第 3 名 0.33 分。这时候会发生什么？

> 一路的第 1 名（1.0 分）**超过**另一路的第 2 名 + 第 3 名之和（0.5 + 0.33 = 0.83）。

也就是说，**单路的强信号过于霸道**——只要在一路里排第一，另一路怎么看都无所谓了。这违背了融合的初衷：我们想要的是「两条路都认可」比「一条路极力推荐」更可信。

**k 是一个平滑项**，把曲线整体压平。取 $k=60$ 时：

| 排名 | $1/(60+\text{rank})$ |
| :-: | :-- |
| 1 | 1/61 ≈ 0.01639 |
| 2 | 1/62 ≈ 0.01613 |
| 3 | 1/63 ≈ 0.01587 |
| 50 | 1/110 ≈ 0.00909 |

第 1 名和第 2 名的差距被压缩到几乎可以忽略，而「被两路同时召回」带来的**加和**优势就凸显了出来。

### 两个极限

理解 k 最好的方式是看它的两端：

- **$k \to 0$**：退化为纯 $1/\text{rank}$。头部极度霸道，接近「谁在某一路排第一谁就赢」。
- **$k \to \infty$**：所有排名的分数趋于相等（都约等于 $1/k$）。此时 RRF 退化为**投票**——只数一个文档被几路召回了，完全不管排在第几。

60 落在中间偏「投票」的一侧。这个值来自 Cormack、Clarke、Buettcher 在 2009 年提出 RRF 时的实验设置，此后在信息检索领域被广泛沿用为默认值。

**本项目直接采用了这个约定俗成的默认值，没有在自己的数据上调过。**

### 一个具体算例

光看公式不直观，算一遍就清楚了。假设两个文档：

- **文档 X**：ES 排第 1，向量排第 50。（一路极强，一路很弱）
- **文档 Y**：ES 排第 5，向量排第 5。（两路都中等偏上）

$$
\text{score}(X) = \frac{1}{60+1} + \frac{1}{60+50} = 0.01639 + 0.00909 = 0.02548
$$

$$
\text{score}(Y) = \frac{1}{60+5} + \frac{1}{60+5} = 0.01538 + 0.01538 = 0.03076
$$

**文档 Y 胜出。**

这就是 RRF 想要的行为：**两路一致认可的中等排名，胜过一路极力推荐、另一路不认的结果。** 直觉上也说得通——两个独立的检索系统都觉得它相关，比一个系统单方面看好更可信。

## 三、代码走读

项目里 RRF 用在两个地方，逻辑几乎相同：

- `searchContentHybrid()`（`:365`）——用户私人内容的混合搜索。
- `searchSimilarNoteIds()`（`:506`）——社区推荐相似笔记。

### 两路并行

`SearchServiceImpl.java:443`：

```java
java.util.concurrent.CompletableFuture.allOf(esFuture, vectorFuture).join();
List<Long> esIds = esFuture.get();
List<Long> vectorIds = vectorFuture.get();
```

两路检索用 `CompletableFuture.supplyAsync` 各自提交，`allOf(...).join()` 汇合。

**必须并行**，因为两路之间没有任何依赖：ES 查询不需要向量结果，向量检索也不需要 ES 结果。串行执行的话总延迟是两者之和，而并行只付出较慢那一路的时间。这是融合方案相比单路检索最主要的额外成本，能省则省。

### 融合本身

`SearchServiceImpl.java:451-460`：

```java
Map<Long, Double> rrfScores = new java.util.HashMap<>();

// 处理 ES 结果
for (int i = 0; i < esIds.size(); i++) {
    Long id = esIds.get(i);
    rrfScores.merge(id, 1.0 / (k + i + 1), Double::sum);
}

// 处理 向量 结果
for (int i = 0; i < vectorIds.size(); i++) {
    Long id = vectorIds.get(i);
    rrfScores.merge(id, 1.0 / (k + i + 1), Double::sum);
}
```

核心就这几行，两处细节值得注意。

**`+ 1` 不能漏。** `i` 是 Java 的下标，从 0 起；而 RRF 公式里的 rank 从 1 起。漏掉 `+1` 会让第一名的分母变成 $k$ 而不是 $k+1$——这个 bug 不会让程序崩溃，也不会让结果明显错乱（排序在多数情况下仍然正确），属于那种能悄悄潜伏很久的错误。

**`merge` + `Double::sum` 正是公式里的 $\sum$。** 一个文档同时被两路召回时，`merge` 第二次遇到这个 key，就把两个分数加起来——这一行代码直接对应第二节算例里文档 Y 的那个加法。用 `merge` 而不是 `containsKey` 判断再取值相加，少一次查表也少一处出错空间。

### 每路内部的权重是另一回事

`SearchServiceImpl.java:387`：

```java
.fields("title^3", "content", "summary^2", "tags")
```

标题权重 3、摘要权重 2、正文和标签权重 1。

这是**路内**的权重，和 RRF 的**跨路**融合是两个层次的事：

```
ES 内部：title^3 / summary^2 加权 ──→ 得出 ES 自己的排名 ──┐
                                                          ├─→ RRF 跨路融合
Qdrant 内部：余弦相似度            ──→ 得出向量自己的排名 ──┘
```

先在 ES 内部把标题匹配抬高（标题里出现查询词，通常比正文里出现更说明主题相关），得到一个排名；RRF 只消费这个**排名**，完全不关心它是怎么算出来的。这个分层是 RRF 好用的原因之一——**它对每一路的内部实现完全不做假设**。

### 只取 ID，不取正文

`SearchServiceImpl.java:399-419` 的 `SourceFilter` 只 include `id` 字段；向量侧对应的是 `.setWithPayload(...setEnable(false)...)`（`:428`），源码注释直接写着「不需要 payload，只要 ID」。

融合阶段只需要 ID 和名次，正文完全用不上——真正的详情在融合、排序、分页之后，才从 MySQL 按最终的那一页 ID 去取。候选数是 60，而每页可能只展示 10 条，提前把 60 篇笔记的正文从 ES 拉回来，五分之四都会被丢掉。

### 同一套融合，两种权限模型

这是本篇最有意思的一处对比。

`searchContentHybrid`（私人搜索，`:365`）按 `userId` 过滤：

```java
.must(m -> m.term(t -> t.field("userId").value(userId)))
```

`searchSimilarNoteIds`（社区推荐，`:506`）反过来——`:521-522`：

```java
.must(m -> m.term(t -> t.field("isPublic").value(1)))
// Removed userId filter to recommend from whole community
.must(m -> m.multiMatch(mm -> mm
        .fields("title^3", "content", "summary^2", "tags")
        .query(text)))
```

那行注释「Removed userId filter to recommend from whole community」记录了一次**有意的**权限模型切换：推荐要跨用户召回，只能看公开笔记。

**同一套 RRF 融合逻辑服务两个权限模型完全相反的场景**——一个「只看自己的」，一个「只看别人公开的」。这说明融合层和权限层是正交的，权限约束全部下推到了各路检索的 filter 里。

两个方法的候选数策略也不同：

```java
final int candidateSize  = Math.max(size * 2, 60);   // :369  混合搜索
final int candidateLimit = Math.max(limit * 3, 50);  // :512  相似推荐
```

推荐场景取 `limit * 3`，倍率更高——因为推荐最终只要 4 条左右，候选池太小的话 RRF 没有区分空间。

### 详情查询的双重收口

`SearchServiceImpl.java:478-482`：

```java
List<ContentItem> contentItems = contentItemMapper.selectList(
        new LambdaQueryWrapper<ContentItem>()
                .in(ContentItem::getId, pagedIds)
                .eq(ContentItem::getUserId, userId));
```

检索侧已经按 `userId` 过滤过了，这里取详情时**又过滤了一次**。

这不是冗余，是有意的纵深防御。原因在于**数据源的可信度不同**：

- ES 和 Qdrant 里的数据是**异步同步**过去的（见 [05 篇](05-异步链路与最终一致性.md)），可能滞后、可能因为同步失败而残留脏数据、可能在笔记权限变更后还没更新。
- MySQL 是唯一的事实来源。

所以最终返回给用户的数据，以 MySQL 的归属判断为准再卡一道。索引数据用来**排序**是安全的，用来**授权**则不够。

## 四、为什么不用分数加权

| 方案 | 为什么不用 |
| :--- | :--- |
| **分数加权求和** `α·BM25 + β·cosine` | 量纲不可比，就是第一节的核心问题。BM25 无稳定上界，α 和 β 没有可推导的取值依据，只能瞎调，且换个语料就得重调 |
| **Min-Max 归一化后加权** | 归一化范围由**当次结果集**决定：同一篇文档在查询甲下归一化成 0.9、在查询乙下归一化成 0.3，两者不可比。结果集只有一条时更是直接退化（min = max） |
| **Z-score 标准化后加权** | 比 Min-Max 稳一些，但仍需假设分数近似正态分布，BM25 的分布明显右偏，假设不成立 |
| **ES 8.x 原生 RRF / knn 混合检索** | ES 8.x 确实内置了 RRF，能省掉应用层的这套融合代码。**这是事后才了解到的选项，不是当时评估后放弃的**——如实说明。代价是要把向量能力绑到 ES 上，而本项目的向量在 Qdrant，迁移成本不小 |
| **只用其中一路** | 第一节的两个场景各证明了一路不够 |

关于 ES 原生 RRF 那一条：面试时**不要说成「我对比后选择了自己实现」**。事后了解到更好的方案是很正常的事，如实说「当时不知道 ES 有原生支持，现在知道了，但迁移要动向量存储，收益不足以覆盖成本」，比编一个评估过程可信得多。

## 五、追问预演

### 第一层：RRF 的 k 为什么取 60？

讲第二节的平滑作用和两个极限：$k \to 0$ 时头部霸道，$k \to \infty$ 时退化成投票，60 落在中间偏投票一侧。

然后明确说明：**这个值沿用自 Cormack 等人 2009 年提出 RRF 时的实验设置，在信息检索领域是通行默认值，本项目没有在自己的数据上调过。**

### 第二层：改成 10 会发生什么？

方向是清楚的——k 变小，曲线变陡，头部权重上升。$k=10$ 时第 1 名得 1/11 ≈ 0.0909，第 5 名得 1/15 ≈ 0.0667，差距比 $k=60$ 时大得多。融合结果会更接近「取两路各自的头部」，而不是「取两路都认可的」。

用第二节的算例复算一下就很直观：$k=10$ 时文档 X 得 $1/11 + 1/60 = 0.1076$，文档 Y 得 $1/15 \times 2 = 0.1333$，Y 仍然赢但优势缩小了；$k$ 再小到 1，X 就会反超。

**但具体在本项目数据上哪个更好，没测过。** 原因同 [02 篇](02-召回精排两段式检索.md)第五节第一层——没有标注评测集，任何参数调整都无法验证。这是整条检索链路的共性短板。

### 第三层：你说 RRF 靠排名规避了量纲问题。但这有个前提——两路的排名要有可比的质量。如果 ES 那路根本没匹配上，返回了 60 条勉强沾边的结果，它们照样会拿到 1/61、1/62 的分数去污染融合结果。你怎么处理的？

**当前实现没有处理。这是 RRF 的固有代价，不是实现疏漏。**

把逻辑讲清楚：RRF 用「只看排名」换来了「量纲无关」，但**排名里不含绝对质量信息**。「第 1 名」只说明它在这一路里最靠前，完全没说它到底相不相关。

回到第一节的场景 B——用户搜「怎么让搜索既准又能理解意思」，BM25 匹配不上任何有效词条。但 ES 不会返回空，它会返回一堆勉强沾边的结果（比如只匹配上了「搜索」这个常见词的笔记）。这些垃圾结果照样进入融合，照样按 1/61、1/62 领分。

如果向量那一路的结果比较分散（没有某一篇被强烈推荐），这些 ES 垃圾就可能靠着「稳定的中等分数」挤进最终结果。

**两种缓解手段，代码里都没有：**

1. **每路设最低分数门槛**——低于门槛的结果不进入融合。这等于把「绝对质量」这个信息重新引入进来，但只用作准入判断、不用作排序依据，避开了量纲问题。
2. **按每路的整体质量给动态权重**——比如 ES 最高分很低时，说明这一路没匹配上，降低它的整体权重。

顺带一提，这个「返回了但都不相关」的问题，恰恰是[重排](03-自建重排服务与降级设计.md)能治的——交叉编码器会给真正不相关的候选打低分。但本项目的重排只用在 RAG 链路，没有用在搜索链路上。

### 追加：你这个混合搜索的分页 total 是准的吗？

不准，且两个方法不准的方式还不一样。见第六节第 2 条——这是个容易被追到的点，值得提前准备。

## 六、现有实现的坑与改进方向

### 1. RRF 常数 `k = 60` 硬编码两处

`SearchServiceImpl.java:367` 和 `:511` 各写了一次：

```java
final int k = 60;                 // :367  searchContentHybrid
final int k = 60; // RRF constant // :511  searchSimilarNoteIds
```

改一处会漏另一处，两个方法的融合行为就此不一致。

**改进**：提为类常量或配置项。既然第五节承认了「没调过」，那至少让它**可调**。

### 2. 两处分页 total 都不准，且成因完全不同

**不要把这两个混为一谈**，面试被追问时说错了会很难看。

**`searchContentHybrid`**（`:468`）：

```java
int total = sortedIds.size();
```

`sortedIds` 是融合后的候选 ID 集合，大小受 `candidateSize = Math.max(size * 2, 60)`（`:369`）封顶，两路合起来最多 120 左右。语料里真有 500 条命中，前端也只会看到 total 约等于 120。**分页总数被候选池大小截断了。**

**`searchContentSemantic`**（`:354`）：

```java
return new PageImpl<>(resultList, PageRequest.of(page, size), resultList.size()); // Qdrant 不易获取 Total，暂时用
```

这里的 total 是**当前页的条数**，源码注释已经承认了——向量数据库通常不返回精确总数。这个更离谱：翻到第 2 页时 total 仍然只是第 2 页的条数。

**改进**：混合搜索可以在 ES 侧单独发一次 `count` 请求拿真实总数；语义搜索则应该明确告诉前端「总数未知」，改用游标分页而不是页码分页。

### 3. ES 分支静默降级

`SearchServiceImpl.java:409-410`：

```java
} catch (Exception e) {
    log.error("混合搜索 - ES查询失败", e);
    return Collections.emptyList();
}
```

ES 挂掉时返回空列表，融合照常进行——**混合检索无声退化成纯向量检索**。用户搜 `ConcurrentModificationException`（场景 A）会得到一堆语义相近但不精确的结果，而没有任何迹象表明检索降级了。

向量侧（`:437-438`）、以及 `searchSimilarNoteIds` 的两路（`:544-545`、`:586-587`）都是同样的处理。

这与 [03 篇](03-自建重排服务与降级设计.md)第六节第 1 条是**完全同一类问题**：降级做对了（不阻断），可观测没做（没人知道降级了）。同一个毛病在这个项目里出现了两次，说明它是个系统性的习惯问题，不是偶然。

**改进**：至少在返回结果里带一个 `degraded` 标记，让调用方知道这次结果只有一路。

### 5. `syncAll` 先清空再逐条写，同步期间索引不可用

`SearchServiceImpl.java:624` 和 `:644`：

```java
noteRepository.deleteAll();    // 清空原有 Note
...
contentRepository.deleteAll(); // 清空原有 Content
```

两个问题：

- **同步期间索引是空的或半空的。** 这期间所有搜索请求都会返回空结果或不完整结果，而且——结合第 3 条——用户看到的是「搜不到」，不是「正在维护」。
- **逐条 `save()`，没有用 ES 的批量 API。** 数据量上来之后会很慢，而慢又直接延长了上一条的不可用窗口。

**改进**：用别名切换。写一个新索引 → 数据写完后原子地把别名指过去 → 删旧索引。全程旧索引一直可用，切换是瞬时的。这是 ES 全量重建的标准做法。

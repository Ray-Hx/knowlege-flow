# 05 · 异步链路与最终一致性

> 前四篇讲检索。本篇换个视角：那些被检索的数据，是怎么从 MySQL 流到 Elasticsearch、Qdrant、Neo4j 的。
>
> 这个项目在这件事上有个很好的教学价值——**同一个代码库里同时存在教科书级的正确实现和明显有问题的实现**。本篇的主线就是把这两条路摆在一起看。
>
> 涉及代码：`RabbitMQConfig.java`、`EngagementSyncProducer.java`、`EngagementSyncConsumer.java`、`AiProcessConsumer.java`、`GraphSyncListener.java`、`NoteServiceImpl.java`

---

## 一、这个问题为什么难

用户点「保存笔记」。这一下要触发的事情有：

| 做什么 | 写到哪 | 大概要多久 |
| :--- | :--- | :--- |
| 保存正文 | MySQL | 很快 |
| 更新全文索引 | Elasticsearch | 一次网络往返 |
| 分块 → 嵌入 → 建向量索引 | Qdrant | 上百次嵌入（见 [01 篇](01-分块策略-从固定长度到语义切分.md)） |
| 解析 `[[链接]]` → 建关系 | Neo4j | 一次网络往返 |
| 生成摘要 | LLM | 数秒 |
| 抽取标签 | LLM | 数秒 |

如果同步做完再返回，用户点一次保存要转圈十几秒。这显然不行，所以必须异步——**主流程只写 MySQL 然后立刻返回，其余的慢慢跑。**

但异步一开，三个新问题立刻冒出来：

1. **可靠性**：主库写成功了，异步任务失败了怎么办？用户以为存好了，实际搜不到。
2. **幂等**：消息重复投递、乱序到达怎么办？
3. **时序**：异步任务跑起来的那一刻，主库的事务提交了吗？

第三个最隐蔽——它不像前两个那样一想就能想到，而且出问题时表现为「偶发的、无规律的」失败。**这个项目确实踩了它**，但有意思的是，项目里另一条链路又完美地避开了它。

## 二、原理

### 两套异步机制并存，怎么分工

项目里同时用了 Spring 应用事件（`@EventListener`）和 RabbitMQ（`@RabbitListener`）。这不是历史遗留，两者的能力边界确实不同：

| | Spring 应用事件 | RabbitMQ |
| :--- | :--- | :--- |
| 作用范围 | 进程内 | 跨进程 |
| 持久化 | 无，进程重启即丢 | 队列持久化，重启不丢 |
| 重试 | 无内建机制 | 有，可配死信 |
| 削峰 | 无（`@Async` 线程池满了就阻塞或拒绝） | 有，消息堆在队列里 |
| 成本 | 一次方法调用 | 序列化 + 网络 + broker |

选择标准可以浓缩成一句话：**丢了要不要紧。**

- **丢了不要紧**——因为可以靠全量重建补回来。ES 索引丢了可以 `syncAll()` 重建，图谱关系丢了可以重新解析笔记。这类走 Spring 事件，省掉 MQ 的全部开销。
- **丢了很要紧**——丢了就真丢了，或者重建代价高。AI 摘要丢了要重新花钱调 LLM；点赞计数丢了会让数据长期不一致。这类走 MQ。

### 可靠性阶梯

从弱到强有三档：

```
无重试            ──→   自动重试          ──→   重试 + 死信队列
消费失败即丢          失败重投几次            重试耗尽后转入死信队列
                     仍失败则丢弃            消息保留下来，可人工/补偿处理
```

要点是**死信队列不会自动修复任何东西**。它的作用是「不要静默丢弃」——把反复失败的消息挪到一个单独的队列里存着，让人有机会发现它、检查它、决定怎么处理。没有死信队列，重试耗尽后消息就消失了，连「有东西失败过」这件事都无从得知。

**本项目在这个阶梯上是不齐的**——这是第三节的核心对照。

### 幂等的两条路

消息队列的投递保证通常是「至少一次」，所以重复消费是常态而非异常。应对有两条路：

**路线 A：幂等表。** 记下已处理的消息 ID，消费前查重。通用，但要多一张表、多一次 IO，而且这张表本身还要考虑清理策略。

**路线 B：让操作天然幂等。** 把消费动作设计成「执行多少次结果都一样」。

路线 B 的关键在于**消息里放什么**：

| 消息内容 | 消费动作 | 重复消费的后果 |
| :--- | :--- | :--- |
| `{noteId: 7, delta: +1}` | 计数 += 1 | **多加了**，数据错 |
| `{noteId: 7}` | 从数据库重算计数，覆盖缓存 | 结果相同，**无害** |

差别在于**增量式 vs 覆盖式**。带 `delta` 的消息是增量的，重复执行会累积；只带 `noteId` 的消息把「算什么」的责任交给消费方，消费方每次都以数据库为准重算——重复消费、乱序到达，最终都收敛到同一个结果。

**这是把幂等性设计进消息格式，比事后加一张幂等表更根本。**

### 事务与发布的时序：本篇的核心

现在看第三个问题。

在一个 `@Transactional` 方法里 `publishEvent(...)` 或者发 MQ 消息时，**事务还没有提交**——提交发生在方法返回、代理层切面退出的时候。

这带来什么后果，取决于监听方怎么写：

**情况 1：同步 `@EventListener`。** 监听器在同一个线程、同一个事务里执行，能看到未提交的数据。虽然不干净，但通常不出错。

**情况 2：`@Async @EventListener`。** 监听器跑在**另一个线程**上。那个线程有自己的数据库连接，**看不到当前事务未提交的修改**。它去查这条刚插入的笔记——可能查不到。

**情况 3：直接发 MQ 消息。** 最糟。消息一旦投出去，别的进程可能立刻消费。而此时：
- 事务可能还没提交 → 消费者查不到这条数据；
- 事务甚至可能**回滚** → 消息已经发出去了，指向一条从来不存在的笔记。

情况 3 就是经典的**双写不一致**：数据库和消息队列是两个独立的系统，没有分布式事务把它们绑在一起。

**正确解法**是让「发布」晚于「提交」：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
```

业务代码照常在事务内 `publishEvent`（这一步只是往 Spring 的事务同步器里登记，不做任何实际投递），Spring 在**事务成功提交之后**才回调监听器，此时再发 MQ。事务回滚时监听器根本不会被调用，消息也就不会发出去。

这里还有一个连带的设计问题：**`AFTER_COMMIT` 里发消息失败了怎么办？** 不能往上抛——数据库已经提交了，抛异常既回滚不了事务，又会让用户看到一个「保存失败」的假象。只能记日志，并依赖别的机制兜底。

## 三、代码走读

把两条链路并排看。

### 好的那条：点赞计数同步

**第一步，事务内发布事件。** `NoteEngagementServiceImpl.java:121` 的方法带 `@Transactional`，在 `:144` 发布事件：

```java
eventPublisher.publishEvent(
        new NoteLikeChangedEvent(this, noteId, userId, liked ? "LIKE" : "UNLIKE"));
```

事件类的注释把设计意图写清楚了（`NoteLikeChangedEvent.java`）：

```java
/**
 * 点赞状态变更事件。
 *
 * <p>在事务内发布，由 {@code @TransactionalEventListener(AFTER_COMMIT)} 监听后再投递 MQ。
 * 这样数据库回滚时不会有消息发出，从根本上避免"库里没写成、缓存却改了"的双写不一致。
 */
```

**第二步，提交后才投递。** `EngagementSyncProducer.java:30`：

```java
/**
 * 事务提交成功后才投递消息。
 *
 * <p>发送失败不向上抛出：此时数据库已提交，抛异常既回滚不了事务，
 * 又会让用户看到失败。缓存值由 TTL 到期后回源自愈，代价可接受。
 */
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onLikeChanged(NoteLikeChangedEvent event) {
    EngagementSyncMessage message = new EngagementSyncMessage(
            event.getNoteId(), event.getUserId(), event.getAction());
    try {
        rabbitTemplate.convertAndSend(
                RabbitMQConfig.ENGAGEMENT_EXCHANGE,
                RabbitMQConfig.ENGAGEMENT_SYNC_ROUTING_KEY,
                message);
        log.debug("发送互动计数同步消息: noteId={}, action={}", event.getNoteId(), event.getAction());
    } catch (Exception e) {
        log.error("发送互动计数同步消息失败，缓存将由 TTL 过期后自愈: noteId={}", event.getNoteId(), e);
    }
}
```

这段把第二节最后那个问题回答得很完整：投递失败**不上抛**，而是承认「缓存会短暂不准」，靠 Redis 的 TTL 过期后回源自愈来兜底（缓存 TTL 见 `NoteEngagementServiceImpl.java:60` 的 `redisTemplate.expire`）。**明确地选择了一个可接受的降级后果**，而不是假装不会失败。

**第三步，队列配了死信。** `RabbitMQConfig.java:117-127`：

```java
/**
 * 互动计数同步队列，重试耗尽后转入死信交换机而不是被丢弃
 */
@Bean
public Queue engagementSyncQueue() {
    return QueueBuilder.durable(ENGAGEMENT_SYNC_QUEUE)
            .deadLetterExchange(ENGAGEMENT_DLX)
            .deadLetterRoutingKey(ENGAGEMENT_DLQ_ROUTING_KEY)
            .build();
}

@Bean
public Queue engagementSyncDlq() {
    return QueueBuilder.durable(ENGAGEMENT_SYNC_DLQ).build();
}
```

**第四步，消费者不 catch。** `EngagementSyncConsumer.java:26`：

```java
@RabbitListener(queues = RabbitMQConfig.ENGAGEMENT_SYNC_QUEUE)
public void handleEngagementSync(EngagementSyncMessage message) {
    if (message == null || message.getNoteId() == null) {
        log.warn("忽略无效的互动计数同步消息: {}", message);
        return;
    }

    // 异常向上抛出，触发重试；重试耗尽后进入死信队列
    engagementService.refreshLikeCountFromDb(message.getNoteId(), message.getUserId());
    log.debug("互动计数已同步: noteId={}, action={}", message.getNoteId(), message.getAction());
}
```

**没有 try-catch 是有意为之。** 异常必须向上抛出，Spring AMQP 才会触发重试；catch 住就等于告诉框架「处理成功了」，消息被 ack 掉，重试和死信全都失效。

注意区分两种失败：**消息本身无效**（`noteId == null`）直接 `return`——重试多少次都不会变好，进死信队列也没意义；**处理过程出错**（数据库连不上之类）才抛出去重试。

**第五步，幂等由消息格式保证。** 类注释：

> 以数据库为准重算点赞数并覆盖 Redis。消息只带 noteId，因此重复消费或乱序到达都会收敛到同一结果，无需额外的幂等表。

正是第二节的路线 B。

这条链路五步齐全：**提交后投递 → 投递失败有兜底 → 队列有死信 → 消费者正确抛异常 → 幂等由设计保证。**

现在看 `NoteServiceImpl.createNote`（`:82`）：

**事件在 `:110` 事务内发布，MQ 消息在 `:114-116` 事务内投递。** 而监听方 `GraphSyncListener.java` 是这样的：

    try {

`@Async` + `@EventListener`（**不是** `@TransactionalEventListener`），正是第二节的**情况 2**：监听器立刻在另一个线程执行，去 `getNoteDetail(...)` 回查这条笔记——而事务可能还没提交，**查不到**。

`updateNote`（`:127`，事件在 `:167`、MQ 在 `:171-173`）和 `deleteNote`（`:184`，事件在 `:204`）是同样的写法。

### 这个对比说明了什么

**关键的一点：`@TransactionalEventListener` 这个正确写法，在这个项目里已经存在了**——就在 `EngagementSyncProducer.java:30`，而且连「投递失败为什么不上抛」这种细节都想清楚了、写在注释里了。

所以笔记保存那条路的问题**不是「不知道该怎么做」，而是「知道了但没有回头去改」**。点赞链路大概率是后来重构过的，而笔记保存这条更早的链路保持了原样。

面试时这样讲，比说「我全都设计好了」可信得多，也比说「我不知道有这个注解」显得更有判断力——**你能指出自己代码里两处不一致，并说清哪个对、为什么**。

### AI 队列：可靠性阶梯的另一端

`AiProcessConsumer.java:33`：

```java
@RateLimiter(name = "ai-service")
@RabbitListener(queues = RabbitMQConfig.AI_PROCESS_QUEUE)
public void handleAiProcessTask(AiProcessMessage message) {
    log.info("收到AI处理任务: taskType={}, noteId={}", message.getTaskType(), message.getNoteId());
    try {
        switch (message.getTaskType().toUpperCase()) {
            case "SUMMARY": generateSummary(message); break;
            case "TAG":     extractTags(message); break;
            case "GRAPH":   buildGraphRelations(message); break;
            default: log.warn("未知的AI任务类型: {}", message.getTaskType());
        }
    } catch (Exception e) {
        log.error("AI处理任务失败: taskType={}, noteId={}",
                message.getTaskType(), message.getNoteId(), e);
        // TODO: 可以考虑重试机制或发送到死信队列
    }
}
```

**catch 住了所有异常，只打日志。** 消息被 ack，任务永久丢失。源码里还留着那行未完成的 `// TODO` 注释。

与点赞消费者对照——**同一个项目，一个刻意不 catch 以触发重试，一个 catch 住吞掉异常**。而 `ai.process.queue`（`RabbitMQConfig.java:99-101`）也没有配死信：

```java
@Bean
public Queue aiProcessQueue() {
    return QueueBuilder.durable(AI_PROCESS_QUEUE).build();
}
```

摆在一起就是可靠性阶梯的两端：AI 摘要（丢了要重新花钱调 LLM）停在最低档，点赞计数（可以从数据库重算）反而做到了最高档。**保护级别和数据的重要性是反着的。**

### 限流：MQ 削峰的下半场

`@RateLimiter(name = "ai-service")` 用的是 Resilience4j。

为什么 AI 队列需要限流：MQ 的作用是把突发流量堆在队列里慢慢消费，**但它不会自动控制消费速率**——消费者空闲时，Spring AMQP 会尽可能快地把积压消息推过来。批量导入 100 篇笔记，队列里瞬间堆了 300 个 AI 任务，消费者会以最快速度全部发给 LLM，直接打爆 API 的 QPS 配额或烧掉一大笔钱。

所以：**MQ 削的是入口的峰（请求不会压垮应用），限流削的是出口的峰（应用不会压垮下游）。** 两者是一对，缺一不可。

### 队列全景

`RabbitMQConfig` 声明了 5 个队列、5 个交换机：

| 队列 | 消费者 | 死信 |
| :--- | :--- | :-: |
| `engagement.sync.queue` | `EngagementSyncConsumer` | **有** |
| `ai.process.queue` | `AiProcessConsumer`（catch 吞异常） | 无 |
| `content.fetch.queue` | `ContentFetchConsumer` | 无 |
| `index.update.queue` | `IndexUpdateConsumer` | 无 |
| `learning.reminder.queue` | **无** | 无 |

`learning.reminder.queue` 只在 `RabbitMQConfig.java:41`（常量）和 `:110`（队列 Bean）出现，**没有任何 `@RabbitListener` 消费它**——是一个声明了但尚未启用的预留队列。往里发消息只会无声堆积。

## 四、为什么不用单一的异步机制

| 方案 | 取舍 |
| :--- | :--- |
| **全部同步执行** | 用户等十几秒。不可接受 |
| **全部走 MQ** | 一致性好、语义统一。代价：ES 同步这种可重建的任务也要付序列化 + broker 开销；本地开发必须起 RabbitMQ 才能跑通完整流程，调试成本上升 |
| **全部走 Spring 事件** | 轻量、零依赖。但进程重启丢消息、无重试——AI 摘要跑到一半重启就永久丢失，而这是要花钱重算的 |
| **分场景选择**（本项目） | 按「丢了要不要紧」分流。**但代价是认知负担**：维护者要记住哪条链路走哪套，而两套的失败语义、重试行为、可观测性完全不同。本篇第三节那个不一致，某种程度上就是这个代价的体现 |
| **事务性发件箱（Outbox）** | 消息先写进同库的 outbox 表（与业务同一个事务），再由轮询器投递。能彻底解决第二节的时序问题，且不依赖 `AFTER_COMMIT` 之后投递失败的兜底。代价是多一张表 + 一个轮询器。**本项目未采用**，是明确的改进方向 |

## 五、追问预演

### 第一层：为什么有的走 Spring 事件，有的走 MQ？

讲「丢了要不要紧」这个分流标准，举两个对比：

- ES 索引同步走事件——丢了可以 `syncAll()` 全量重建（见 [04 篇](04-混合检索与RRF融合.md)第六节第 5 条），代价是一次重建。
- AI 摘要走 MQ——丢了要重新调 LLM，既花钱又要重新等待。

### 第二层：你的 AI 队列，消费失败了会怎么样？

**直接承认：catch 住只打日志，消息被 ack，任务永久丢失，源码里还留着那行 `// TODO` 注释。**

然后讲对照：点赞队列做对了——不 catch、抛出去触发重试、配了死信兜底。同一个项目两种做法并存，说明这套异步机制是逐步演进的，点赞那条是后来才补上的。

**主动说出「保护级别和数据重要性是反着的」这个观察**，比等面试官指出来强。

### 第三层：你在 `@Transactional` 方法里发布事件、发 MQ 消息。而 `GraphSyncListener` 是 `@Async @EventListener`。异步线程去查这条笔记的时候，事务提交了吗？

**不一定，这是一个真实的竞态。**

完整讲清楚：`publishEvent` 在 `:110`，事务在方法返回后才提交。`@Async` 监听器立刻在另一个线程执行 `getNoteDetail(...)` 回查数据库，而那个线程用的是另一个连接，看不到未提交的数据——**可能查不到刚插入的笔记**。

实际表现有两层，都很隐蔽：

1. 查不到会走 `GraphSyncListener` 的 catch，打一条 error 日志，**用户侧完全无感**。表现是「图谱里偶尔缺一个节点」，而这种缺失几乎不可能被发现。
2. 是否出问题取决于线程调度和事务提交的相对速度，所以**偶发、难复现**。

MQ 那三条（`:114-116`）更严重：消息一投出去就可能被消费。如果事务随后回滚，消费者会拿到一个**指向不存在笔记的 noteId**。

**修法**：改成 `@TransactionalEventListener(phase = AFTER_COMMIT)`；MQ 投递同样挪到提交后。

**这里一定要主动补一句**：这个正确写法在本项目里已经用过了——`EngagementSyncProducer.java:30` 就是标准实现，连投递失败的兜底策略都想清楚了。所以这不是认知盲区，是没有回头统一。彻底的方案是事务性发件箱。

**能自己指出这个竞态、并指出自己代码里已有正确范例，比藏着被问出来强得多。**

## 六、现有实现的坑与改进方向

### 1. 笔记保存链路在事务提交前发布事件与消息

`NoteServiceImpl.java:82` 的 `@Transactional` 方法内，`:110` 发布事件、`:114-116` 投递 MQ；`GraphSyncListener` 用 `@Async @EventListener` 接收，构成竞态。`updateNote`（`:167`、`:171-173`）与 `deleteNote`（`:204`）同样。

**改进**：改用 `@TransactionalEventListener(phase = AFTER_COMMIT)`，与 `EngagementSyncProducer.java:30` 保持一致。

### 2. 可靠性等级不齐，且与数据重要性相反

5 个队列只有 `engagement.sync.queue` 配了死信（`RabbitMQConfig.java:117-127`），其余 4 个失败即丢。而 AI 任务的重算成本明显高于点赞计数。

**改进**：至少给 `ai.process.queue` 补上死信。

### 3. `AiProcessConsumer` catch 吞掉异常

`AiProcessConsumer.java:33` 的 catch 块只打日志，源码里的 `// TODO` 未处理。即使补了死信队列，只要还 catch 着，消息也永远进不了死信。**这两条要一起改才有效。**

### 4. 异步失败全部静默

`GraphSyncListener` 的两个方法都是 catch 后只打 error 日志。图谱少一个节点，用户不会感知，也没有任何指标或告警。

这与 [03 篇](03-自建重排服务与降级设计.md)第六节第 1 条、[04 篇](04-混合检索与RRF融合.md)第六节第 3 条是同一个毛病——**降级/失败不可观测，在这个项目里出现了三次**，是系统性的习惯问题。

### 5. 无消息追踪，一次保存扇出的任务串不起来

一次 `createNote` 会产生 1 个 Spring 事件 + 3 条 MQ 消息，分别被不同的监听器和消费者处理。消息体里没有任何关联 ID（traceId），日志里也没有。出问题时无法把「这次保存」相关的所有日志串起来查。

**改进**：消息里带 traceId，日志用 MDC 输出。

### 6. `learning.reminder.queue` 声明了但无人消费

`RabbitMQConfig.java:41`、`:110` 声明了队列和交换机绑定，但全项目没有任何 `@RabbitListener` 消费它。目前是预留队列，往里发消息只会无声堆积。

**改进**：要么实现消费者，要么删掉声明——留着一个不工作的队列，会让读代码的人误以为学习提醒功能已经在跑了。

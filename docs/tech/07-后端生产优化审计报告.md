# Backend Optimization Audit & Report

> 审计日期：2026-09-01  
> 范围：Java 17 / Spring Boot 3.5.9 后端、MySQL、Redis、RabbitMQ、Elasticsearch、Qdrant、Neo4j、MinIO 与 AI/RAG 链路  
> 原则：保持现有 HTTP API 和业务语义；不修改表字段，不替换框架，不虚构性能数据

## 0. Executive verdict

项目的业务模块与 RAG 链路已经具备良好的展示价值，本轮修复了多个会导致越权、事务失效、索引失效和资源失控的问题。Java 17 干净测试已通过。

但当前仍不建议直接作为无人值守的生产部署，上线前至少需要解决三个 P1 阻断项：

1. 建立可从空库重现的基线 schema 与 Flyway/Liquibase 迁移链路。
2. 为 MySQL 事实数据到 RabbitMQ/ES/Qdrant/Neo4j 的投影建立 transactional outbox 或等价可补偿机制。
3. 完成 GitHub 凭据的加密持久化，并建立 JWT 实时撤销策略。

## 1. Project architecture

### 1.1 模块与存储

| 模块 | 主要职责 | 主要存储/依赖 |
| --- | --- | --- |
| `user` / `security` | 用户、隐私、关系、私信、JWT/OAuth2 | MySQL、Redis |
| `note` | 笔记、文件夹、版本、双链、点赞/浏览 | MySQL、Redis、RabbitMQ |
| `content` | RSS、GitHub、arXiv、文件抓取与聚合 | MySQL、RabbitMQ、外部 HTTP |
| `search` | BM25 全文、Qdrant 语义、RRF 混合、reranker | Elasticsearch、Qdrant、千问 Embedding |
| `ai` | 对话、摘要/标签、RAG、查询改写、重排 | DeepSeek/OpenAI-compatible LLM、Qdrant、RabbitMQ |
| `graph` | 显式双链与 AI 关系投影 | MySQL 事实表、Neo4j |
| `spaced` / `dashboard` | SM-2 间隔复习、AI 出题、统计 | MySQL、Redis、LLM |
| 公共基础设施 | 异常、配置、对象存储、出站 HTTP、异步执行器 | Spring Boot、MinIO、Actuator |

### 1.2 关键调用链

1. **笔记写入与多存储投影**  
   `NoteController -> NoteServiceImpl -> MySQL commit -> AFTER_COMMIT event -> RabbitMQ -> IndexUpdateConsumer -> ES + Qdrant chunks`；图谱目前仍由进程内 `GraphSyncListener -> Neo4j` 投影。

2. **RAG 问答**  
   `AiController -> AiServiceImpl -> ConversationMemory -> QueryRewriter -> Qwen text-embedding-v4 -> Qdrant candidate recall -> bge-reranker-v2-m3 -> context construction -> DeepSeek chat model -> response persistence`。

3. **混合搜索**  
   `SearchController -> ES BM25 + Qdrant semantic (bounded parallel) -> RRF fusion -> reranker -> pagination -> MySQL detail hydration`。

4. **内容聚合**  
   `ContentSourceController/scheduler -> RabbitMQ -> ContentFetchConsumer -> RSS/GitHub/arXiv adapter -> MySQL -> content event -> index queue`。

5. **复习与 AI 出题**  
   `SpacedController -> SpacedServiceImpl -> ownership check -> LLM question generation -> MySQL -> SM-2 review state`。

## 2. Audit findings

### [P0][Resolved] 默认事务管理器错误指向 Neo4j

- **Location:** `config/TransactionConfig.java`，MySQL service 中的默认 `@Transactional`。
- **Problem:** 多数据源自动配置下，默认 `transactionManager` 可能由 Neo4j 占用，纯 MySQL 写操作看似有事务、实际不会回滚。
- **Why it matters:** 用户、笔记、复习、内容等多表写入可产生半成功数据。
- **Fix:** 显式将 `JdbcTransactionManager` 设为 `@Primary transactionManager`，Neo4j 使用独立 manager/template 和 repository 扫描。
- **Risk:** Medium；多数据源事务绑定属于核心配置，已有上下文断言覆盖。
- **Expected impact:** MySQL `@Transactional` 恢复真实原子性；Neo4j 事务边界可见。

### [P0][Resolved] AI 分析与复习出题存在 IDOR

- **Location:** `AiController/AiServiceImpl`，`SpacedController/SpacedServiceImpl.generateQuestions`。
- **Problem:** 某些入口只传资源 ID，未将当前 `userId` 收口到查询条件。
- **Why it matters:** 猜测 ID 可能读取/重生成他人笔记派生数据。
- **Fix:** service 签名强制传 `userId`，在缓存、删除旧题和 LLM 调用之前验证 `id + userId`。
- **Risk:** Low；未修改 HTTP 路径或返回格式。
- **Expected impact:** 阻断跨用户读写，安全测试覆盖越权路径。

### [P0][Resolved] 无效 LLM 输出可清空旧图谱关系

- **Location:** `graph/service/impl/GraphServiceImpl.java`。
- **Problem:** 旧流程先删关系、再解析模型输出，格式错误时会丢失已有关系；类内调用还会绕过事务代理。
- **Why it matters:** 一次模型幻觉即可破坏用户图谱。
- **Fix:** 远程 LLM 调用放在事务外，完整验证协议/目标归属后，在短 Neo4j 事务内原子替换；重建使用 transaction template。
- **Risk:** Medium；已添加 malformed-output 回归测试。
- **Expected impact:** 无效输出只导致本次失败，不再销毁已有图数据。

### [P0][Resolved] 敏感 API 凭据进入版本配置

- **Location:** `.env` / `.env.example` / `application.yml` / `.gitignore`。
- **Problem:** 开发过程中凭据曾与配置混合，存在误提交风险。
- **Why it matters:** Embedding/LLM 密钥泄漏可导致数据泄漏与费用滥用。
- **Fix:** 真实凭据仅保留在 Git 忽略的 `.env`，跟踪配置只保留环境变量引用和空示例；当前 tracked-files 正则扫描未命中真实 key 样式。
- **Risk:** Low。
- **Expected impact:** 降低后续提交泄密概率。对曾经进入远端历史的 key 仍应在供应商侧轮换。

### [P1][Resolved] RSS/GitHub/arXiv 抓取可被用于 SSRF，且输入/响应无边界

- **Location:** `common/utils/OutboundUrlValidator.java`，`HttpClientUtil.java`，各 fetch service。
- **Problem:** 用户控制 URL 可触达本机/内网/元数据网段，RSS/HTTP body 缺少大小和条目上限。
- **Why it matters:** 可扫描内网、窃取云凭据或用大响应耗尽内存。
- **Fix:** 只允许 public HTTP(S)，拒绝 local/private/link-local/ULA/CGNAT；GitHub/arXiv 使用 host allowlist；每次重定向重新验证；HTTP/RSS 限 5 MiB、feed 限 200 条。
- **Risk:** Medium；极少数内网 RSS 地址将不再可用，这是预期安全边界。
- **Expected impact:** 关闭主要 SSRF 通道，给出站内存与解析工作量确定上限。

### [P1][Resolved] 持久化 XSS 与上传内容伪装

- **Location:** `RssFetchServiceImpl`、`SearchServiceImpl.safeHighlight`、`ImageUploadValidator`、`MinioUtil`。
- **Problem:** 外部 HTML 和 ES highlight 被前端 `v-html` 渲染；上传信任客户端 MIME/扩展名。
- **Why it matters:** 可形成持久化 XSS，或上传伪装脚本/图像炸弹。
- **Fix:** RSS 使用 safelist/纯文本清理；ES highlight 开启 HTML encoder，只放行 `<em>`；回退字段也 HTML escape；Tika + ImageIO 验证真实 JPEG/PNG/GIF、尺寸和像素数。
- **Risk:** Low。
- **Expected impact:** 阻断主要 stored-XSS 与 MIME spoofing 路径。

### [P1][Resolved] 异步资源无界且 Future 可永久等待

- **Location:** `config/AsyncConfig.java`，`AiServiceImpl`，`SearchServiceImpl`，`RagRetriever`，`EmbeddingService`。
- **Problem:** 默认异步/按请求线程可在峰值时无界增长；RAG 和语义搜索曾对 Qdrant 使用无超时 `get()`。
- **Why it matters:** 下游半开时会耗尽请求线程/内存，形成级联故障。
- **Fix:** 应用、AI、搜索使用独立有界 executor，显式队列、拒绝策略和关机等待；RAG/Qdrant/reranker/混合分支设置超时与降级。
- **Risk:** Medium；过载时会明确拒绝或降级，而不是无限堆积。
- **Expected impact:** 线程数、排队量和单次等待均有上限。

### [P1][Resolved] 消息消费失败被吞掉，部分抓取入口是 no-op

- **Location:** `ContentFetchConsumer`，GitHub/arXiv/RSS fetch adapter，`IndexUpdateConsumer`，`AiProcessConsumer`，`RabbitMQConfig`。
- **Problem:** 消费异常记录后返回会被 broker 当成成功；GitHub/arXiv MQ 入口未真正执行；重试耗尽后无 DLQ。
- **Why it matters:** 界面显示“已同步”，实际永久漏抓或漏索引。
- **Fix:** adapter 按 `sourceId + userId + type` 加载并执行；消费者重抛失败；3 次指数退避后分别进入 content/AI/index DLQ；ES 与 Qdrant 统一在索引消费者中幂等处理。
- **Risk:** Medium；故障任务会可见地堆积在 DLQ，需配套监控/重放运维。
- **Expected impact:** 短暂下游故障可自动恢复，永久失败可审计而非静默丢失。

### [P1][Resolved] 文件夹/内容源删除绕过完整生命周期

- **Location:** `NoteFolderServiceImpl.deleteFolder`，`ContentSourceServiceImpl.deleteSource`，`ContentItemServiceImpl.deleteBySource`。
- **Problem:** 直接批量改 deleted 会留下版本、双链、ES/Qdrant/Neo4j 幽灵数据；删源未删其内容。
- **Why it matters:** 已删私有数据仍可能被搜索/RAG 召回。
- **Fix:** 文件夹删除先一次读取用户树，循环/归属校验后逐笔记调用完整 `deleteNote`；删源批量软删内容并发布索引删除事件。
- **Risk:** Medium；大文件夹删除耗时会增加，但正确性优先。
- **Expected impact:** 主库删除与派生存储的补偿链路保持一致。

### [P1][Resolved] 用户禁用、公开隐私和 HTTP 语义未真正生效

- **Location:** `UserDetailsServiceImpl`、`UserPrincipal`、`CommunityController`、`PublicController`、`UserProfileServiceImpl`、`GlobalExceptionHandler`。
- **Problem:** 禁用用户仍可登录；公开主页/统计未统一执行隐私配置；业务错误常包在 HTTP 200 中。
- **Why it matters:** 账号封禁和用户隐私不可信，网关/监控无法根据 HTTP status 识别错误。
- **Fix:** 映射 Spring Security `enabled`；公开 profile/stats 统一校验隐私并移除 email；`BusinessException` 返回真实 4xx/5xx status。
- **Risk:** Medium；依赖“HTTP 200 + body code”的非标准客户端需确认。
- **Expected impact:** 认证、隐私和可观测性语义一致。

### [P1][Resolved] 搜索映射、排序和 N+1 导致结果错误

- **Location:** `SearchServiceImpl`。
- **Problem:** `ContentItem.contentText` 未写入 ES `content`；笔记结果按时间排序覆盖 BM25/title boost；全局搜索合并后再次按时间排序；文件夹名逐条查询。
- **Why it matters:** 标题明确命中仍不靠前，内容正文可能根本不可搜，分页查询数线性增长。
- **Fix:** 显式映射 content；标题完整短语 boost；以 ES `_score` 为主排序、时间仅同分兜底；文件夹一次 `IN` 批量查询。
- **Risk:** Low to Medium；搜索顺序会按“相关性”的预期语义变化。
- **Expected impact:** 文件夹查询从 `1 + N` 降到固定 2 次；标题相关性不再被时间覆盖。

### [P1][Resolved] 混合搜索只融合、没有真正 rerank

- **Location:** `SearchServiceImpl.searchContentHybrid`，`RagRetriever`，`CrossEncoderReranker`。
- **Problem:** 早期混合分支只做 ES/Qdrant RRF，无法在相似主题干扰中利用 query-document 交互信号。
- **Why it matters:** RRF 只融合排名，不能判断深层问题-文档相关性。
- **Fix:** RRF 先扩大候选，分页前经 `BAAI/bge-reranker-v2-m3` 交叉编码器精排；超时/异常回退 RRF/向量顺序；返回下标做越界、去重验证。
- **Risk:** Medium；额外一次网络/推理延迟，已由 3.5 s 上限和降级保护。
- **Expected impact:** 提高前 K 结果精度的机会；实际提升必须使用标注集对比 nDCG/MRR/Recall，本报告不声称百分比。

### [P1][Resolved] 私信会话列表全量加载历史并 N+1 查用户

- **Location:** `UserMessageMapper.selectConversationSummaries`，`MessageServiceImpl.getConversations`。
- **Problem:** 会话页需将用户全部消息加载到 JVM，再对联系人逐个查询。
- **Why it matters:** 复杂度随历史消息总量增长，容易形成大对象与查询风暴。
- **Fix:** MySQL 8 CTE/window function 一次完成联系人、最新消息、未读数和用户 join，最多返回 200 会话。
- **Risk:** Medium；依赖 MySQL 8，与项目声明版本一致。
- **Expected impact:** JVM 加载从 `O(全部历史消息)` 降为 `O(会话数 <= 200)`，service 层数据库往返降为 1 次。

### [P1][Open] 新环境无法从仓库重建 MySQL schema

- **Location:** `docker/mysql/init.sql`，`docker/mysql/migrations/V2..V8`，当前已删除的基线 schema 文件。
- **Problem:** init 只创建数据库/用户，V2..V8 只是增量且没有 Flyway/Liquibase 执行器，基线表定义不完整。
- **Why it matters:** 容器空卷或灾备环境无法启动，也无法证明测试/生产 schema 一致。
- **Recommended fix:** 从受控基准数据库导出 V1 baseline，引入 Flyway，将 V2..V8 幂等化并在 CI 中从空库启动。
- **Risk:** High；需核对真实生产 schema 和数据迁移，本轮按要求未擅自改表。
- **Expected impact:** 可重现部署、可回滚迁移、可审计 schema 历史。

### [P1][Open] MySQL 与消息/搜索/图投影仍非原子

- **Location:** `NoteAiProcessListener`、`SearchSyncListener`、`GraphSyncListener`、各 producer。
- **Problem:** AFTER_COMMIT 保证了“不在 DB 回滚前投影”，但进程在 commit 后、publish 前崩溃仍会永久漏消息；publisher confirms/returns 也未完整配置。
- **Why it matters:** MySQL 已成功，ES/Qdrant/Neo4j/AI 任务可不可见，形成无声不一致。
- **Recommended fix:** 以 MySQL transactional outbox 记录事件，独立 publisher 用 confirm 投递并标记；消费者按 `eventId` 幂等；保留全量重建作最终补偿。
- **Risk:** High；涉及 schema 和运维流程，不应在本轮小步修改中仓促引入。
- **Expected impact:** 将投影从“尽力而为”提升为“至少一次 + 幂等”。

### [P1][Open] GitHub 订阅凭据实际不可持久化

- **Location:** `SysUserProfile.githubToken` (`@TableField(exist = false)`)，`GitHubFetchServiceImpl`。
- **Problem:** fetcher 依赖 token，但 entity 明确排除数据库映射，也没有安全的凭据写入流程。
- **Why it matters:** GitHub 功能在重启/新请求后稳定报“未配置 token”。
- **Recommended fix:** 设计独立 credential 表，密文使用 KMS/envelope encryption，只提供 write-only API，记录轮换/撤销时间；不应把明文 token 放进 profile JSON。
- **Risk:** High；需 schema、密钥管理与迁移。
- **Expected impact:** 修复 GitHub 集成的真实可用性，同时不降低凭据安全。

### [P1][Open] JWT 无法实时撤销

- **Location:** `JwtAuthenticationTokenFilter.java`，`jwt.expiration=7d`。
- **Problem:** 过滤器完全信任已签名 claims，用户被禁用、改密码或改角色后，旧 token 在 7 天内仍有效。
- **Why it matters:** 被封禁/泄漏的会话无法立即止损。
- **Recommended fix:** access token 缩短至 15–30 分钟，refresh token 轮换；引入 `tokenVersion`/`passwordChangedAt` 或低 TTL 状态缓存，高风险操作强制查状态。
- **Risk:** Medium to High；会改变登录会话生命周期，需前端协同。
- **Expected impact:** 禁用/改密码可在可控时间内生效。

### [P1][Open] LLM/RAG 远程调用仍处于 JDBC 长事务内

- **Location:** `AiServiceImpl.sendMessage`，`SpacedServiceImpl.generateQuestions/addNoteToReview`。
- **Problem:** 查询/写入 MySQL 后，事务持有连接等待最长 120 s LLM 或 RAG 网络调用；`addNoteToReview` 类内调用还绑定预生成题目。
- **Why it matters:** 慢模型会占满 Hikari 连接池，并放大锁等待。
- **Recommended fix:** 用短事务保存用户消息/任务状态，事务外调用 LLM，再用第二个短事务 CAS 保存结果；失败显式标记可重试。
- **Risk:** High；需定义“用户消息已保存但 AI 失败”的产品语义。
- **Expected impact:** 连接占用时间从远程请求级降为本地 SQL 级。

### [P1][Open] MinIO bucket 公开读

- **Location:** `docker-compose.yml` 中 `mc anonymous set public`。
- **Problem:** 知道对象 URL 即可匿名读取，对用户私有附件/头像的产品语义过于宽松。
- **Why it matters:** URL 泄漏、历史日志或 referrer 可暴露私有文件。
- **Recommended fix:** bucket 改私有，下载通过授权 API 生成短 TTL presigned URL；按 userId/objectId 校验所有权。
- **Risk:** Medium to High；会影响已存 URL 与前端缓存，需迁移方案。
- **Expected impact:** 对象访问恢复用户级授权边界。

### [P1][Open] RAG 对不可信上下文的 prompt-injection 隔离不足

- **Location:** `RagRetriever.build`。
- **Problem:** RSS/笔记文本直接拼进 system-like 参考区，提示还允许“资料不足用通用知识补充”，与可引用 RAG 的不可回答语义冲突。
- **Why it matters:** 内容中的“忽略之前指令”可诱导模型偏离问题；资料不足时易生成无引用幻觉。
- **Recommended fix:** system message 明确将 context 视为数据而非指令，使用结构化分隔；增加 answerability gate；默认仅基于证据回答，通用知识补充必须明示。
- **Risk:** Medium；会改变回答风格，应使用不可回答和注入测试集验证。
- **Expected impact:** 降低检索内容对模型控制流的影响和无证据回答率。

### [P2][Open] 图谱投影仍是进程内异步且重建存在 N+1

- **Location:** `GraphSyncListener`，`GraphServiceImpl.syncNote/rebuildGraph`。
- **Problem:** listener 失败只记录，无持久重试；每条边逐个查 MySQL/读 Neo4j，重建随节点+边数增长。
- **Why it matters:** 进程崩溃可漏投影，大图重建慢。
- **Recommended fix:** 复用 outbox/MQ；批量读取 target notes，Neo4j 使用 UNWIND 批量 upsert；用指标观测 projection lag。
- **Risk:** Medium。
- **Expected impact:** 重建往返从边数级降为批次级。

### [P2][Open] dashboard/SM-2 仍有 JVM 聚合与循环 SQL

- **Location:** `DashboardServiceImpl.getYearlyHeatmap`，`SpacedServiceImpl.initReviewQueue`。
- **Problem:** 热力图读取用户全部 note IDs 再大 `IN`；初始化队列用 list `contains` 和逐笔记 select/insert，还可串行调 LLM。
- **Why it matters:** 大用户数据下产生长 SQL、O(N²) CPU 和 N 次数据库/远程往返。
- **Recommended fix:** 使用 SQL `GROUP BY DATE(...)` 分类聚合；active IDs 改 HashSet；review 用 batch insert/select；出题与队列初始化解耦。
- **Risk:** Medium；需核对时区与统计口径。
- **Expected impact:** 从传输明细行改为传输天级聚合；初始化从 O(N² + N SQL) 降为 O(N + batch SQL)。

### [P2][Open] 全量索引重建先 `deleteAll`，失败时可留下半个索引

- **Location:** `SearchServiceImpl.syncAll`。
- **Problem:** 直接清空活跃索引后逐条 save，中途错误被逐条记录并继续。
- **Why it matters:** 重建窗口搜索不可用，且完成后也可能缺文档。
- **Recommended fix:** 新建带版本索引，bulk 导入+校验 count/失败清单，成功后原子切 alias，再延迟删旧索引。
- **Risk:** Medium；需索引命名和运维策略。
- **Expected impact:** 重建期搜索仍可用，失败可安全丢弃新索引。

### [P2][Open] 可观测性缺少关键链路 SLI

- **Location:** 全局日志/Actuator/RabbitMQ/RAG。
- **Problem:** 已有日志但缺少统一 requestId/traceId、MQ lag/DLQ depth、projection lag、RAG recall/rerank/LLM 分段延迟与降级比例。
- **Why it matters:** 出现“MySQL 有数据但搜不到”时难以定位所在阶段。
- **Recommended fix:** Micrometer timer/counter + trace correlation，Prometheus 报警 DLQ depth、executor queue/rejection、Qdrant/reranker timeout、outbox age。
- **Risk:** Low to Medium；需控制 label 基数，不将 userId/query 当 metric label。
- **Expected impact:** 将不一致和降级从用户投诉变为可主动告警。

## 4. Implemented changes by engineering dimension

### 4.1 Correctness and transactions

- 分离 JDBC/Neo4j transaction manager，修复默认事务失效。
- 修复 AI 分析、复习出题、公开主页/统计的所有权与隐私边界。
- 笔记/内容删除走完整生命周期，避免派生存储残留。
- 内容同步 `lastSyncTime` 只在真实成功后更新。
- 图关系在外部输出完整验证后再原子替换。

### 4.2 Performance

- 搜索文件夹名从 N+1 改为一次批量查询。
- 私信会话从全历史加载 + N+1 改为单条聚合 SQL，最多 200 行返回 JVM。
- 内容页用批量查询代替逐条补充；dashboard 多处查询只 select 所需列。
- AI 标签任务增加 Redis cooldown 和 100 条上限，避免每次 dashboard 访问制造成本风暴。
- 异步线程池、搜索候选、HTTP/RSS body、上传文件、RAG/Qdrant 等待均增加明确上限。

### 4.3 Stability

- RabbitMQ 消费失败可重试，重试耗尽进专用 DLQ。
- ES + Qdrant 索引进入同一幂等消费链路，不再由进程内 listener 吞失 ES 异常。
- 取消每请求创建线程，异步未捕获异常有统一处理。
- Qdrant/reranker/混合分支超时后可降级，`InterruptedException` 恢复中断标记。
- 应用启动后浏览量回写有 initial delay，不在上下文刚启动时立即打 Redis。

### 4.4 Security

- 修复 IDOR、隐私开关、禁用账户登录、密码序列化。
- 关闭 SSRF 主通道，外部响应不再回显给客户端。
- 搜索高亮/RSS/文件上传增加 XSS/内容校验。
- Redis serializer 移除危险的宽泛默认类型信息。
- JWT dev 未配置时每进程生成随机 key，显式配置的 key 过短则拒绝启动；prod 必须注入。

### 4.5 Maintainability and local configuration

- dev 应用与 Compose 统一从 `.env` 读 MySQL/Redis/Neo4j/RabbitMQ/MinIO 参数，避免容器和应用密码漂移。
- test 的外部基础设施集成类只在 `KNOWLEDGE_FLOW_RUN_INTEGRATION_TESTS=true` 时执行，普通 `mvn test` 不依赖本机 Docker。
- 全局异常映射使用真实 HTTP status，DTO 补充边界校验。
- 新增安全、事务、检索、消息重试、删除生命周期、RAG 超时等回归测试。

## 6. Performance evidence and limitations

本轮没有在与生产同规模数据上运行 JMH、APM 或 `EXPLAIN ANALYZE`，因此不给出“提升 XX%”的结论。可直接从代码证明的变化是：

- 文件夹名查询：`1 + N` 数据库往返 -> 固定 2 次。
- 私信会话：加载全部历史 + N 个用户查询 -> 1 条数据库聚合 SQL，JVM 最多 200 会话。
- 异步执行：从不可控的默认/临时线程 -> 有界 queue 与确定拒绝策略。
- RAG/Qdrant：潜在无限等待 -> 可配置 5 s 上限与降级。
- HTTP/RSS/图像：不受控响应/解码 -> 明确字节、条目、尺寸和像素上限。

建议下一轮使用以下基线验证：

1. 10k/100k/1M notes/messages 的 `EXPLAIN ANALYZE` 和 p50/p95/p99。
2. RAG 标注集分别运行 vector-only、RRF、RRF+reranker，记录 Recall@20、MRR@5、nDCG@5、answerable accuracy 和不可回答误答率。
3. 断开 ES/Qdrant/RabbitMQ/Neo4j 进行 chaos test，观测超时、DLQ、重试和投影恢复。
4. 对 executor queue/rejection、Hikari active/pending、GC pause 和远程 API 延迟做压测前后对比。

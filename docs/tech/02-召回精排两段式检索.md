# 02 · 召回精排两段式检索

> [01 篇](01-分块策略-从固定长度到语义切分.md)把文档切成了片并建好了索引。本篇讲怎么把**对的**片取出来——为什么向量检索一步到位不够，为什么要拆成「召回」和「精排」两段。
>
> 涉及代码：`src/main/java/com/ray/knowledgeflow/module/ai/service/RagRetriever.java`（191 行）、`Reranker.java`（39 行）

---

## 一、这个问题为什么难

假设知识库里有一篇《Qdrant 接入笔记》，其中散落着这样几个切片：

- **切片 P**：「Qdrant 的集合创建需要指定向量维度和距离度量方式，配置不当会导致后续写入失败。」
- **切片 Q**：「Qdrant 客户端的连接参数在 QdrantConfig 中集中配置，包括 host、port 和 gRPC 通道选项。」
- **切片 R**：「gRPC 的 timeout 参数默认值偏大，网络抖动时请求会长时间挂起，建议显式设短。」

用户提问：**「Qdrant 的连接超时怎么配？」**

向量检索按余弦相似度排序，返回 top-5。结果是：

| 排名 | 切片 | 为什么排在这 |
| :-: | :--- | :--- |
| 1 | 切片 Q | 「Qdrant」「连接」「配置」三个词全中，相似度最高 |
| 2 | 切片 P | 「Qdrant」「配置」命中 |
| 3-5 | 同篇的其他切片 | 都带「Qdrant」，语义邻近 |
| **8** | **切片 R** | 用词是「timeout 参数」而非「连接超时」，「gRPC」而非「Qdrant」，语义距离更远 |

**唯一真正回答了问题的切片 R，排在第 8 位，被 top-5 截断在外。**

### 核心矛盾：相似 ≠ 能回答

向量检索排序依据的是「语义邻近度」，而我们真正想要的是「相关性」——这个片段能不能回答这个问题。两者高度相关，但**不等价**：

- 切片 Q 与问题**语义邻近**（都在讲 Qdrant 的连接配置），但它只说了「参数在 QdrantConfig 里」，没说超时怎么配。
- 切片 R 与问题**语义较远**（措辞完全不同），但它恰恰是答案。

用统计学的话说，语义相似度是我们对「相关性」这个真正目标的**代理指标**（proxy）。代理指标好用、可预计算、能建索引，但它和目标之间的偏差，会在 top-K 截断这一步被放大成硬错误——排第 6 和排第 5 的差别，从「分数略低」变成了「模型完全看不到」。

本篇要解决的是：**能不能在截断之前，用一个更贴近「相关性」的方式重新排一次序。**

---

## 二、原理

答案是能，但不能用同一个模型。这里需要理解两种检索模型的结构差异。

### 双编码器（bi-encoder）：能建索引，但看不见对方

向量检索用的模型是双编码器。它的结构是：

```
query    ──→ [编码器] ──→ 向量 q ─┐
                                  ├─→ cos(q, d)
document ──→ [编码器] ──→ 向量 d ─┘
```

关键性质：**query 和 document 各自独立编码，编码时互相看不见。**

这个性质带来一个巨大的工程优势——**document 的向量可以离线预计算**。百万篇文档提前算好向量存进 Qdrant 建索引，查询时只需算一次 query 的向量，然后做近似最近邻搜索。这正是向量检索能在百万级语料上做到毫秒级响应的根本原因。

但代价也来自同一个性质：编码切片 R 的时候，模型**根本不知道**用户会问什么。它只能生成一个「通用的、面向所有可能问题的」语义表示。于是「timeout 参数默认值偏大」这句话被编码成一个关于「超时配置」的通用向量，而没有任何机会去针对「Qdrant 的连接超时怎么配」这个具体问题，把自己的相关性表达出来。

### 交叉编码器（cross-encoder）：看得见对方，但不能建索引

交叉编码器把两者拼成一个序列送进同一个模型：

```
[CLS] query [SEP] document [SEP] ──→ [编码器] ──→ 相关性分数
```

注意力层让 query 的每个 token 都能直接「看到」document 的每个 token，模型可以针对这个具体问题去判断这个文档有没有回答它。上面的例子里，交叉编码器能捕捉到「连接超时」与「timeout 参数」「请求会长时间挂起」之间的对应关系——这是双编码器在独立编码时无法建立的联系。

精度显著更高，但代价是致命的：**分数依赖具体的 query，无法预计算。** N 个文档就要跑 N 次前向。在百万级语料上直接用它，每次查询要跑一百万次前向推理，完全不可行。

### 两者是级联关系，不是替代关系

| | 双编码器 | 交叉编码器 |
| :--- | :--- | :--- |
| query 与 document 交互 | 无 | 逐 token 交互 |
| 可否预计算 | **可以**，能建索引 | 不可以 |
| 适用规模 | 百万级 | 几十条 |
| 优化目标 | 召回率（别漏） | 精确率（别错） |

于是自然得到两段式：

```
        ┌─────────── 召回 ───────────┐   ┌────── 精排 ──────┐
query → │ 双编码器 + Qdrant 近邻搜索 │ → │  交叉编码器重排  │ → top-5 → 拼 prompt
        │   百万级 → 20 条候选       │   │  20 条 → 5 条    │
        └────────────────────────────┘   └──────────────────┘
             快，宽进，保召回率              慢，严出，保精确率
```

### 候选数与 topK 的约束关系

这两个数字不能随便定，它们之间有硬约束。

**候选数必须明显大于 topK。** 如果候选 20、topK 5，精排可以从 20 条里挑出最好的 5 条——它有权改变**结果集的成分**。但如果候选 5、topK 5，精排只能改变这 5 条的顺序，无法把第 8 名换进来。而第一节那个例子里，问题恰恰是「答案在第 8 名」——**精排救不回召回阶段没捞上来的东西。**

**但候选数受精排延迟约束。** 交叉编码器每个候选跑一次前向，候选翻倍延迟就翻倍，而精排处在用户请求的关键路径上。

本项目取 **候选 20、精排 5**（`RagRetriever.java:42-47`）。

## 三、代码走读

整个两段式集中在 `RagRetriever.retrieve()`（`:83`）一个方法里。这个类的存在本身有个背景——类注释写道「检索逻辑原先在同步问答和流式问答里各写了一遍，此处统一」。现在两个调用点分别是 `AiServiceImpl.java:152`（同步问答）和 `:221`（流式问答）。

### 三个配置参数

`RagRetriever.java:41-51`：

```java
/** 召回阶段候选数，需明显大于 topK 才有精排空间 */
@Value("${app.rag.retrieve.candidate-size:20}")
private int candidateSize;

/** 精排后送入生成模型的片段数 */
@Value("${app.rag.retrieve.top-k:5}")
private int topK;

/** 向量相似度下限 */
@Value("${app.rag.retrieve.score-threshold:0.5}")
private float scoreThreshold;
```

第一条注释「需明显大于 topK 才有精排空间」正是第二节推导出的那条约束。

### 召回阶段

`RagRetriever.java:91-100`：

```java
Points.SearchPoints searchPoints = Points.SearchPoints.newBuilder()
        .setCollectionName(CHUNK_COLLECTION)
        .addAllVector(vector)
        .setLimit(candidateSize)
        .setFilter(userFilter(userId))
        .setWithPayload(Points.WithPayloadSelector.newBuilder().setEnable(true).build())
        .setScoreThreshold(scoreThreshold)
        .build();

List<Points.ScoredPoint> candidates = qdrantClient.searchAsync(searchPoints).get();
```

`setFilter(userFilter(userId))` 这一行值得单独说。它把用户隔离**下推到了向量库侧**，而不是取回结果之后在 Java 里过滤。

这个选择不是性能优化，而是**正确性要求**。如果先取 20 条再在应用层滤掉别人的笔记，那 20 个候选名额会被别人的笔记占掉——一个笔记很少的新用户，可能 20 条里有 18 条是别人的，过滤后只剩 2 条进入精排。候选数从 20 塌缩到 2，精排空间几乎没了。下推到向量库侧，则保证捞回来的 20 条**全部是**这个用户的。

过滤条件本身在 `:179`：

```java
private static Points.Filter userFilter(Long userId) {
    return Points.Filter.newBuilder()
            .addMust(Points.Condition.newBuilder()
                    .setField(Points.FieldCondition.newBuilder()
                            .setKey("userId")
                            .setMatch(Points.Match.newBuilder().setInteger(userId).build())
                            .build())
                    .build())
            .build();
}
```

### 精排阶段

`RagRetriever.java:107-112`：

```java
List<String> texts = candidates.stream()
        .map(p -> payloadString(p, "content"))
        .toList();
List<Integer> ranked = reranker.rerank(query, texts, topK);
log.info("RAG 精排: {} -> {}", candidates.size(), ranked.size());
```

只有五行，但接口设计值得留意：**传进去的是字符串列表，拿回来的是下标列表**，而不是重排后的文本或者重排后的 `ScoredPoint`。

这个选择让 `Reranker`（`Reranker.java:27`）完全不需要知道 Qdrant 的存在：

```java
List<Integer> rerank(String query, List<String> candidates, int topK);
```

它只处理「一个问题 + 一堆字符串」，返回「按相关性排好的下标」。带来三个好处：

1. **可单测**——不需要起 Qdrant，直接喂字符串数组断言下标顺序。
2. **可替换**——三种重排实现（见 [03 篇](03-自建重排服务与降级设计.md)）都只面对这个签名。
3. **不丢信息**——返回下标而非文本，调用方拿着下标能回到原始 `ScoredPoint`，score、payload、sourceId 都还在。若返回文本，这些元数据就得再匹配一次。

### 三条降级路径

`RagRetriever.retrieve()` 里有三处降级，全部收敛到同一个出口：

```java
// :86  向量算不出来
List<Float> vector = embeddingService.embed(query);
if (vector.isEmpty()) {
    return RagContext.empty(query);
}

// :103 一条都没召回
if (candidates.isEmpty()) {
    return RagContext.empty(query);
}

// :117 被中断
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    log.warn("RAG 检索被中断，降级为原始 prompt");
    return RagContext.empty(query);
// :121 其他任何异常
} catch (Exception e) {
    log.warn("RAG 检索失败，降级为原始 prompt: {}", e.getMessage(), e);
    return RagContext.empty(query);
}
```

而 `RagContext.empty()`（`:71`）做的事是：

```java
/** 未检索到内容时，使用原始问题 */
static RagContext empty(String query) {
    return new RagContext(query, new ArrayList<>());
}
```

**prompt 就是用户的原始问题，引用列表为空。** 也就是说 RAG 挂掉时，系统退化成一个普通的 LLM 问答——模型用通用知识回答，答案质量下降，但用户不会看到报错。

这是一个明确的产品取向：**RAG 是增强，不是前提。** 值得注意 `InterruptedException` 被单独捕获并调用了 `Thread.currentThread().interrupt()` 恢复中断标志——捕获中断异常后不恢复标志，会让上层的线程池、超时控制失效。

### 拼装

`RagRetriever.build()`（`:128`）按重排后的下标顺序，把切片依次拼进 prompt：

```java
StringBuilder contextBuilder = new StringBuilder("以下是参考资料：\n\n");
...
contextBuilder.append("--- [").append(title).append("] ---\n")
        .append(content).append("\n\n");
...
contextBuilder.append("请基于以上参考资料回答用户的问题。如果资料不足，请用你的通用知识补充。问题：\n")
        .append(query);
```

末尾那句「如果资料不足，请用你的通用知识补充」与降级设计是一致的取向——即使检索成功但资料不对题，也给模型留了回退余地。

引用列表则按 `sourceId` 去重（`:149` 的 `addedSourceIds.add(sourceId)`）：同一篇笔记的多个切片只在引用里显示一次。**注意这里去重的只是引用展示，prompt 内容没有去重**——这一点在第六节展开。

## 四、为什么不用单段检索

| 方案 | 为什么不用 |
| :--- | :--- |
| **只用向量 top-5，不做重排** | 就是第一节的失败场景。**但要诚实说明**：这是绝大多数 RAG 入门实现的做法，在语料规模小、问题措辞与文档措辞接近时完全够用。重排的收益随语料增大、问题措辞越偏离原文而增大 |
| **加大 topK 到 20，全部塞进 prompt** | 表面上「反正都给模型，让它自己挑」。两个问题：一是上下文窗口和 token 成本都涨；二是更本质的——长上下文里模型对**中段**内容的利用率显著下降（业界称为 lost in the middle），塞更多不等于用得上更多。把筛选责任推给生成模型，不如在检索侧解决 |
| **用交叉编码器直接扫全库** | 无法预计算，百万级语料每次查询要跑百万次前向。这是第二节讲的结构性限制，不是工程优化能解决的 |
| **调高 `score-threshold` 来提精度** | 阈值卡的是**余弦相似度**，而第一节的问题恰恰是「相似度高但不相关」（切片 Q）和「相似度低但相关」（切片 R）。调高阈值只会把切片 R 滤得更早，把切片 Q 留得更牢——**方向是反的** |

最后一条值得强调：面对「检索不准」，调阈值是最容易想到的动作，但它治不了「代理指标与真实目标偏离」这个病。要治这个病，只能换一个更贴近真实目标的打分方式——这正是重排在做的事。

## 五、追问预演

### 第一层：候选 20、精排 5，这两个数怎么定的？

先讲约束关系（第二节末尾那两条）：候选必须明显大于 topK 才有精排空间；候选数上限由精排延迟决定。

然后**必须承认**：20/5 是在这两条约束下取的经验值，**没有跑评测集调过参**。项目里没有标注好的问答评测集，因此无法量化「候选 30 比 20 好多少」。

这个「没有评测集」是本项目检索链路的共性短板，[01 篇](01-分块策略-从固定长度到语义切分.md)的百分位阈值、[04 篇](04-混合检索与RRF融合.md)的 RRF 常数都是同一个问题。主动说出来，比每个参数都编一套调参故事可信。

### 第二层：`score-threshold` 设了 0.5，这会不会把正确答案在召回阶段就滤掉？

**会，而且这是两段式最脆弱的地方。**

两段式的前提是「召回阶段尽量宽，把可能相关的都捞回来，由精排负责筛」。而 `scoreThreshold` 是在**召回阶段**做的硬过滤——被它滤掉的候选，精排永远看不到。**召回阶段的损失，精排救不回来。**

第一节的切片 R 就是典型：它的相似度本来就不高，如果低于 0.5 就会在召回阶段直接消失，后面重排做得再好也无济于事。

0.5 这个值还有一个隐患：它是**绝对阈值**。不同嵌入模型输出的相似度分布不同——有的模型即使不相关的文本对也普遍给到 0.6 以上，有的模型相关文本对也只有 0.4。换模型后 0.5 未必仍然合适，需要重新标定。

这与 [01 篇](01-分块策略-从固定长度到语义切分.md)第二节讨论的「绝对阈值 vs 相对阈值」是完全同一类问题——同一个坑在这条链路上出现了两次。

### 第三层：你的 `userFilter` 是在 Qdrant 侧过滤的。那 payload 里的 `userId` 字段建索引了吗？

**这是本篇最该老实承认的一处。**

代码只调用了 `setFilter(...)`（`:95`），**没有在任何地方为 `userId` 这个 payload 字段显式创建索引**。`EmbeddingService.createCollection()` 只创建了集合和向量配置，没有 `createPayloadIndex` 之类的调用。

为什么这要紧：向量数据库的过滤查询，在 payload 字段有索引和没索引时，执行策略可能完全不同。没有索引时，过滤条件无法高效地参与近邻搜索的剪枝，可能导致实际返回的候选数少于 `limit` 指定的 20 条——**在近似最近邻搜索里，过滤与检索的交互本来就微妙**。

**诚实的表述是：这一点没有验证过。** 日志里 `log.info("RAG 召回: query={}, candidates={}", ...)`（`:101`）实际打出了候选数，但没有系统性地观察过它是否稳定等于 20。

正确的做法是给 `userId` 建 payload 索引，并观察召回数是否符合预期。这是明确的待办，不是已完成的设计。

## 六、现有实现的坑与改进方向

### 1. `userId` payload 字段未建索引

见第五节第三层。可能影响实际召回数量，且未经验证。

**改进**：在 `EmbeddingService.createCollection` 中补 payload 索引创建；用 `:101` 那行日志核对实际候选数是否稳定为 `candidateSize`。

### 2. `score-threshold` 是绝对阈值，换模型需重新标定

`RagRetriever.java:50-51`。见第五节第二层。

**改进**：改为按候选分布取相对阈值，或至少在换嵌入模型时把它列入必改项清单。

### 3. prompt 内容未按来源去重，同一笔记可占满 topK

`build()`（`:128`）里 `addedSourceIds` 只对**引用列表**去重，prompt 拼接不受影响。

后果是：如果某篇笔记的 5 个切片都排进了 top-5，模型看到的上下文全部来自同一篇文档，来源多样性为零。用户界面上引用只显示 1 条，看起来「只检索到一篇」，实际却消耗了全部 5 个名额。

**改进**：在精排后按 `sourceId` 做多样性约束（如同一来源最多取 2 个切片），或采用最大边际相关（MMR）之类的多样性重排。

### 4. 候选数与 topK 未经评测验证

见第五节第一层。缺少标注评测集是根因。

**改进**：即使不做完整评测，也可以人工构造二三十个问答对作为回归集，让参数调整有据可依。

### 5. 无检索结果缓存

同一个问题重复提问，会完整重跑「嵌入 → 向量检索 → 重排」全流程。嵌入和重排都是有成本的外部调用。

**改进**：按 `(userId, query)` 归一化后缓存检索结果，设较短的过期时间。注意笔记更新后需失效。

# 01 · 分块策略：从固定长度到语义切分

> 本篇讲 RAG 链路的第一步——把文档切成片。这是整条链路里最容易被草率处理、但对最终效果影响最直接的一环。
>
> 涉及代码：`src/main/java/com/ray/knowledgeflow/module/ai/service/SemanticChunker.java`（259 行）、`ChunkingService.java`（285 行）

---

## 一、这个问题为什么难

先看一个真实会发生的失败。

假设知识库里有一篇讲检索融合的笔记，其中一段是：

> ……RRF 通过排名而非分数进行融合，因此天然规避了不同检索系统之间的量纲问题。常数 k 取 60，这个取值来自 Cormack 等人 2009 年提出 RRF 时的实验设置，此后在信息检索领域被广泛沿用为默认值。

现在按每 500 字符切一刀。很不巧，刀口落在了「常数 k 取 60，」之后：

- **切片 A** 结尾：`……规避了不同检索系统之间的量纲问题。常数 k 取 60，`
- **切片 B** 开头：`这个取值来自 Cormack 等人 2009 年……`

用户提问：「RRF 的 k 为什么取 60？」

向量检索会命中**切片 A**——它包含「RRF」「k」「60」，与问题的语义重合度最高。检索环节从任何指标上看都成功了：召回率 100%，相似度分数很高。但切片 A 里根本没有「为什么」，答案在切片 B 里，而切片 B 因为不含「k」「60」这些词，语义距离更远，没能进入 top-K。

于是模型拿着一段没有答案的资料，去回答一个它其实有资料可答的问题。**这类错误在日志里完全看不出来**——检索没报错，模型也没报错，只是答得不对。

### 矛盾在哪

分块要同时满足两个互相拉扯的要求：

| 要求 | 为什么 | 推动切片变 |
| :--- | :--- | :--- |
| 切片要够小 | 嵌入模型有输入长度上限；且一个切片里塞太多主题，向量会变成几个主题的平均，对每个主题都不精确（语义被稀释） | 小 |
| 切片要够完整 | 切片是检索的最小单位，也是喂给模型的最小单位。一个不完整的论述，检索到了也没用 | 大 |

定长切分对这对矛盾**完全无感知**。它只认字符数，不关心第 500 个字符落在句子中间、论述中间还是章节中间。它把「切片大小」这一个可控变量做到了最优（长度绝对均匀），却把「切片完整性」完全交给了运气。

本篇要解决的就是：**如何让刀口落在语义的接缝处，而不是字符数的整数倍处。**

## 二、原理

核心思路一句话：**先找出所有可能的边界，再判断哪些边界处语义真的发生了变化，只在那里切。**

拆成五步，每步回答「为什么需要它」。

### 第 1 步：切成句子——把候选边界的集合缩小

语义边界不可能落在词的中间，最细也就到句子级别。所以先按标点把文本切成句子，后续只在**句子之间**考虑要不要断开。

这一步把「在 5000 个字符位置里选切点」变成了「在 120 个句子间隙里选切点」，问题规模小了一个数量级，且排除了所有明显荒谬的切点。

### 第 2 步：为每个句子求向量——但不能只用单句

有了句子，接下来要判断相邻两句是不是在讲同一件事。自然的做法是把每句转成向量再比较。

但**单句向量的噪声很大**。考虑这样一串句子：

```
① Qdrant 的集合创建需要指定向量维度。
② 那么问题来了。
③ 换嵌入模型之后维度对不上怎么办？
```

句 ② 是个纯过渡句，它的向量几乎不携带任何主题信息——「那么问题来了」放在任何一篇文章里都成立。如果直接用单句向量算距离，会发现 ①→② 距离很大、②→③ 距离也很大，于是在一个根本不该断的地方连断两刀。

解决办法是**滑动窗口**：求句子 i 的向量时，不用句子 i 本身，而用「句子 i 及其前后各 `bufferSize` 句拼接后的文本」。上例中句 ② 的窗口变成 `①②③` 拼接，主题信息由邻居提供，噪声被平滑掉。

这个窗口向量代表的不是「这句话讲什么」，而是**「这个位置附近在讲什么」**——而我们要找的正是「附近在讲什么」发生突变的位置。

### 第 3 步：算相邻窗口的余弦距离

$$\text{cosine\_distance}(a, b) = 1 - \frac{a \cdot b}{\|a\| \, \|b\|}$$

- 余弦相似度取值 $[-1, 1]$，故余弦距离取值 $[0, 2]$。
- 值越大，表示两个位置的语义差异越大。

**为什么用余弦而不用欧氏距离？** 嵌入向量的语义信息主要编码在**方向**上而非模长上。同一个主题写 3 句和写 30 句，向量方向接近但模长可能差很多。欧氏距离会把这种长度差异算成语义差异，余弦不会。

对 n 个句子，得到 n−1 个相邻距离，构成一个序列。切点就藏在这个序列的峰值里。

### 第 4 步：阈值怎么定——本篇的核心

现在有了距离序列，问题变成：**多大的距离才算「语义跳变」？**

最直觉的做法是定一个绝对阈值，比如 0.3，超过就切。**这个做法会失败，原因是不同文档的距离分布差异极大。**

考虑两篇文档：

- **文档甲**是一篇术语密集的技术笔记，一句讲 Qdrant、下一句讲 Elasticsearch、再下一句讲 RabbitMQ。即使这三句同属「架构选型」这一个主题，相邻句的向量距离也普遍偏大，可能都在 0.35 上下。
- **文档乙**是一篇娓娓道来的学习心得，通篇围绕一个话题反复申说。哪怕真的换了大主题，相邻距离也可能只有 0.15。

绝对阈值 0.3 用在这两篇上：

| | 文档甲（距离普遍 ~0.35） | 文档乙（距离普遍 ~0.12，换主题处 0.15） |
| :--- | :--- | :--- |
| 阈值 0.3 的效果 | 几乎每句都超阈值 → **切得粉碎**，每个切片一句话 | 没有一处超阈值 → **一刀不切**，整篇一个切片 |

两种失败都很严重，而且是同一个阈值造成的。

**改用分位数就绕开了这个问题。** 不问「距离有多大」，改问「这个距离在本文档所有距离里排第几」：

> 取所有相邻距离的**第 85 百分位**作为阈值，超过它的位置切开。

这句话的含义是：**不管这篇文档整体的距离水平如何，都在它自己最突兀的那 15% 的位置断开。** 阈值从「绝对量」变成了「相对于本文档分布的相对量」，因此对文档风格免疫——文档甲和文档乙各自按自己的分布定阈值，都能得到合理的切分密度。

### 第 5 步：收尾——语义边界不保证长度均匀

语义切分只保证「切在该切的地方」，完全不保证切出来的片长度合理。可能出现：

- 一个只有十几个字的切片（比如一个孤立的标题行），单独嵌入几乎没有检索价值。
- 一个几千字的切片（比如一整段连贯的长论述），超出嵌入模型输入上限。

所以必须有一道收尾：**短片向前合并，超长片强制拆开**。这一步是对语义切分结果的工程修正，本身不涉及语义判断。

## 三、代码走读

按上面五步的顺序看代码。所有实现集中在 `SemanticChunker.java`。

### 主流程

`SemanticChunker.java:64`：

```java
public List<String> chunk(String text) {
    if (text == null || text.trim().isEmpty()) {
        return List.of();
    }

    List<String> sentences = splitSentences(text);
    if (sentences.isEmpty()) {
        return List.of();
    }
    // 句子太少时无从比较语义距离，直接按长度收尾
    if (sentences.size() < 3) {
        return enforceSizeLimits(sentences, minChars, maxChars);
    }

    List<List<Float>> embeddings = embeddingService.embedAll(buildWindows(sentences, bufferSize));
    if (embeddings.size() != sentences.size()) {
        log.warn("语义切片降级为定长切分: 句子数={}, 向量数={}", sentences.size(), embeddings.size());
        return fixedSizeFallback(text, maxChars);
    }

    List<Double> distances = adjacentDistances(embeddings);
    double threshold = percentile(distances, breakpointPercentile);

    List<String> chunks = assemble(sentences, distances, threshold, maxChars);
    return enforceSizeLimits(chunks, minChars, maxChars);
}
```

五步与代码一一对应：`splitSentences` → `buildWindows` + `embedAll` → `adjacentDistances` → `percentile` + `assemble` → `enforceSizeLimits`。

注意两条**降级路径**，它们的存在理由是同一个：**索引链路不能因为嵌入服务抖动而中断**。

- `sentences.size() < 3`：只有一两句话时，相邻距离最多一个，分位数无意义，直接走长度收尾。
- `embeddings.size() != sentences.size()`：嵌入服务返回数量对不上，说明调用出了问题，退回纯定长切分。切得不够好，总比这篇笔记索引不进去、彻底搜不到强。

### 第 1 步：句子切分

`SemanticChunker.java:54` 和 `:57`：

```java
private static final Pattern SENTENCE_END = Pattern.compile("(?<=[。！？；!?;])|(?<=\\.)(?=\\s)");
private static final Pattern HEADING = Pattern.compile("^\\s{0,3}#{1,6}\\s");
```

`SENTENCE_END` 里藏着一个容易踩的坑。中文标点（`。！？；`）可以直接断句，因为它们几乎不出现在别的语境里。但**英文句点不行**——`3.14`、`Node.js`、`v1.2.3` 里都有句点，直接按 `\.` 断句会把它们劈开，`Node.js` 变成 `Node` 和 `js` 两句。

解决办法是那个 `(?<=\\.)(?=\\s)`：两个零宽断言组合，要求「前面是句点」**且**「后面是空白字符」才断。`Node.js` 里句点后面跟的是 `j` 不是空白，所以不断；`……的实现。 下一句` 里句点后面是空格，断。

`HEADING` 让 Markdown 标题行整行成为一个独立句子（`splitSentences`，`:96`）。这实际上是把「按结构切分」的一半保留了下来——标题天然是语义边界，不需要靠向量去发现。

### 第 2 步：滑动窗口

`SemanticChunker.java:119`：

```java
static List<String> buildWindows(List<String> sentences, int bufferSize) {
    if (bufferSize <= 0) {
        return sentences;
    }
    List<String> windows = new ArrayList<>(sentences.size());
    for (int i = 0; i < sentences.size(); i++) {
        int from = Math.max(0, i - bufferSize);
        int to = Math.min(sentences.size(), i + bufferSize + 1);
        windows.add(String.join("", sentences.subList(from, to)));
    }
    return windows;
}
```

`bufferSize` 默认 1（`:48`），即每个窗口含 3 句。`Math.max` / `Math.min` 处理首尾边界——第一句没有前驱，窗口就只有 2 句，不做特殊处理也不影响正确性。

注意**返回的窗口数量与句子数量严格相等**，这是主流程里 `embeddings.size() != sentences.size()` 那个校验能成立的前提。

### 第 3 步：余弦距离

`SemanticChunker.java:146`：

```java
static double cosineDistance(List<Float> a, List<Float> b) {
    if (a == null || b == null || a.isEmpty() || a.size() != b.size()) {
        return 0.0;
    }
    double dot = 0, normA = 0, normB = 0;
    for (int i = 0; i < a.size(); i++) {
        double x = a.get(i), y = b.get(i);
        dot += x * y;
        normA += x * x;
        normB += y * y;
    }
    if (normA == 0 || normB == 0) {
        return 0.0;
    }
    return 1.0 - dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
```

两处防御都返回 `0.0` 而非抛异常，语义是「距离为零 = 不切」。选这个方向是有讲究的：**异常情况下宁可少切也不要乱切**。零向量或维度不匹配说明数据有问题，此时切开纯属瞎猜，不如保持连续。

`adjacentDistances`（`:135`）在此基础上生成长度为 n−1 的距离序列。

### 第 4 步：分位数

`SemanticChunker.java:169`：

```java
static double percentile(List<Double> values, int p) {
    if (values == null || values.isEmpty()) {
        return Double.MAX_VALUE;
    }
    List<Double> sorted = new ArrayList<>(values);
    Collections.sort(sorted);
    if (sorted.size() == 1) {
        return sorted.get(0);
    }
    double rank = (p / 100.0) * (sorted.size() - 1);
    int lower = (int) Math.floor(rank);
    int upper = (int) Math.ceil(rank);
    if (lower == upper) {
        return sorted.get(lower);
    }
    return sorted.get(lower) + (rank - lower) * (sorted.get(upper) - sorted.get(lower));
}
```

三个细节：

1. **空列表返回 `Double.MAX_VALUE`。** 又是「宁可不切」的取向——阈值取无穷大，后续 `assemble` 里没有任何距离能超过它，等于一刀不切。
2. **`rank = (p/100) * (size - 1)` 里为什么是 `size - 1`。** 因为下标从 0 起。第 0 百分位应当落在下标 0，第 100 百分位应当落在下标 `size-1`，所以映射区间是 `[0, size-1]` 而不是 `[0, size]`。写成 `size` 会让 p=100 时下标越界。
3. **线性插值。** `rank` 通常不是整数，比如 `size=10`、`p=85` 时 `rank = 0.85 × 9 = 7.65`。取下标 7 和 8 之间按 0.65 的比例插值，比直接取整更平滑，样本少时差别尤其明显。

### 第 4 步（续）：按阈值聚合

`SemanticChunker.java:190`：

```java
static List<String> assemble(List<String> sentences, List<Double> distances,
        double threshold, int maxChars) {
    List<String> chunks = new ArrayList<>();
    StringBuilder current = new StringBuilder(sentences.get(0));

    for (int i = 1; i < sentences.size(); i++) {
        String sentence = sentences.get(i);
        boolean semanticBreak = distances.get(i - 1) > threshold;
        boolean tooLong = current.length() + sentence.length() > maxChars;

        if (semanticBreak || tooLong) {
            chunks.add(current.toString());
            current = new StringBuilder(sentence);
        } else {
            current.append(sentence);
        }
    }
    chunks.add(current.toString());
    return chunks;
}
```

`semanticBreak || tooLong` 这个双条件是**语义与长度两个约束的汇合点**：优先按语义切，但语义不切的地方如果已经攒得太长，也强制切。这里的 `tooLong` 是提前拦截，避免把问题全部推给后面的 `enforceSizeLimits` 去硬拆。

`distances.get(i - 1)` 的下标偏移要留意：`distances[j]` 是句子 j 和 j+1 之间的距离，所以判断「要不要在句子 i 之前断开」用的是 `distances[i-1]`。

### 第 5 步：尺寸收尾

`SemanticChunker.java:216` 的 `enforceSizeLimits` 分两轮：

- **第一轮合并**：若上一个已收集的切片短于 `minChars`（默认 80，`:40`），且合并后不超过 `maxChars`，就把当前切片并进去。
- **第二轮硬拆**：仍然超过 `maxChars`（默认 1000，`:44`）的，按字符暴力切开。

第二轮是整个实现里唯一「明知不好但没有更好办法」的地方——详见第六节。

真正值得注意的是 `ChunkingService.java:63`：

```java
String textToEmbed = String.format("标题：%s 摘要：%s 标签：%s\n%s",
                item.getTitle() != null ? item.getTitle() : "",
                item.getSummary() != null ? item.getSummary() : "",
```

**嵌入的文本 ≠ 存储的文本。** 求向量时把标题、摘要、标签拼在切片前面，但 payload 里存的仍是原始切片。

这么做是为了补偿分块的固有损失：一个切片脱离了全文语境后，可能完全看不出它属于哪篇文档。比如某篇《Qdrant 接入笔记》里有个切片只写了「维度要和模型对齐，否则 upsert 会报错」——单看这句，检索「Qdrant 维度问题」时未必能命中，因为切片里根本没有「Qdrant」三个字。把标题拼进待嵌入文本，向量就带上了文档级的语境。

而 payload 保持原文，是因为**送进模型的上下文不该有这些冗余前缀**——每个切片都带一遍标题摘要标签，会白白占用上下文窗口。

集合创建见 `ChunkingService.java:36`，向量维度 **2048**。

## 四、为什么不用定长切分

三种主流方案的对比。**先说结论：定长 + 重叠是当前 RAG 工程的主流默认选择，语义切分并非普遍更优。**

| 方案 | 优点 | 本项目为什么没用 / 用了 |
| :--- | :--- | :--- |
| **定长 + 重叠窗口**<br>（如 512 字符，overlap 50） | 实现简单、零嵌入开销、切片长度完全可预测、便于估算索引规模 | 重叠只能**缓解**截断不能**消除**——重叠 50 字符时，跨度超过 50 字符的完整论述照样被劈开。且重叠部分重复入库，索引膨胀，同一段内容会被重复召回，挤占 top-K 名额 |
| **按 Markdown 结构切**<br>（按标题层级） | 零嵌入开销、边界天然合理、可解释性最好 | 完全依赖作者的标题习惯。一个二级标题下写三千字就退化成一个超长片，而随手记的笔记常常没有标题。**注意：本项目实际保留了这个策略的一半**——`HEADING` 正则让标题行强制成为语义边界（`:57`），相当于「结构信号免费用，其余靠向量判断」 |
| **语义切分**（本项目） | 对文档风格免疫（分位数阈值）、边界贴合语义 | 代价是每次分块要为每个句子窗口求一次向量，见第六节 |

### 什么时候语义切分不划算

要诚实划定适用边界：

- **文档结构清晰时**（规范的技术文档、有完整标题层级的文章），按结构切又快又准，语义切分是多余的。
- **文档很短时**（几百字的随手笔记），压根不需要切，本实现的 `sentences.size() < 3` 分支就是在处理这种情况。
- **索引量极大时**，每篇文档多出的嵌入调用会累积成显著成本。

语义切分的收益集中在**结构松散的长文本**上——个人笔记恰好大量属于这一类，这是本项目选它的实际理由。

## 五、追问预演

### 第一层：为什么百分位取 85？

85 控制的是**切片粒度**：取值越大，超过阈值的位置越少，切得越少、每片越长；取值越小切得越碎。

需要老实说明的是：**85 是一个经验起点，不是推导或调参得出的结果。** 它作为配置项暴露在 `app.rag.chunk.breakpoint-percentile`（`:35-36`），可以调，但本项目**没有跑过评测集去比较不同取值的效果**——因为没有标注好的问答评测数据。

不要把这个说成「我测试了 70/85/95 三组」。面试官追问「你的评测集怎么构造的、用什么指标」时会立刻穿帮。

### 第二层：分位数阈值有个隐患——如果整篇文档语义高度连贯，最大的距离也很小，你还是会在第 85 百分位处切一刀。这合理吗？

**不合理，这是分位数方案的固有代价。**

分位数保证了「总会切」，因为百分位阈值必然落在已有的距离值之间，必然有 15% 的位置超过它。哪怕这篇文档从头到尾在讲同一件事、所有相邻距离都在 0.05 上下，实现照样会在最大的那几个 0.06 处切开——而 0.06 根本不代表语义跳变。

这正是绝对阈值的镜像问题：绝对阈值对分布不敏感，相对阈值对**分布的绝对水平**不敏感。两者各丢了一半信息。

**缓解办法是叠加一个绝对下限**：距离低于某个值时，无论它在分布里排第几都不切。这样对连贯文档就退化成「整篇一个切片」（再由 `enforceSizeLimits` 按长度处理），符合直觉。**当前实现没有做这一层保护**，属于明确的改进点。

### 第三层：每个句子都要求一次向量。一篇五千字的笔记大概一百多个句子，索引一篇笔记的开销你能接受吗？

先澄清一个可能的误解：**不是一百多次 HTTP 往返。** 代码用的是 `embeddingService.embedAll(...)`（`:78`），批量接口，所有窗口一次提交。

但嵌入的 **token 成本**确实与句子数成正比，而且比想象的更高——因为用的是滑动窗口，`bufferSize=1` 时每个句子会出现在 3 个窗口里，实际送去嵌入的总 token 量约为原文的 **3 倍**。

更实际的问题是**重复计算**：用户编辑一篇笔记只改了一段，重新索引时整篇的所有窗口都要重新求向量，未改动的部分白算一遍。当前实现没有任何缓存。

这个开销可以接受的前提是**分块发生在异步链路里**（见 [05 篇](05-异步链路与最终一致性.md)），用户点保存后立即返回，不等索引完成。如果分块在同步路径上，这个方案不可行。

## 六、现有实现的坑与改进方向

### 1. 无嵌入缓存，编辑笔记会全量重算

`SemanticChunker.chunk()`（`:64`）每次调用都对全文所有窗口重新求向量。改一个错别字，整篇重算。

**改进**：按句子内容哈希缓存向量。笔记编辑通常只影响局部，缓存命中率会很高。

### 2. 分位数保证「总会切」，缺绝对下限保护

见第五节第二层。连贯文档会被切在不该切的地方。

**改进**：`assemble`（`:190`）的 `semanticBreak` 判断加一个绝对下限，`distances.get(i-1) > threshold && distances.get(i-1) > minDistance`。

### 3. `enforceSizeLimits` 的硬拆退回了定长切分

`SemanticChunker.java:216` 第二轮：

```java
for (int i = 0; i < chunk.length(); i += maxChars) {
    result.add(chunk.substring(i, Math.min(chunk.length(), i + maxChars)));
}
```

超长切片按字符暴力截断——**这正是本篇开篇批评的那个问题**。语义切分辛苦找到的边界，在超长片上完全失效，退化成第一节里那个 RRF 例子的情形。

**改进**：超长片应当递归调用语义切分（用更低的百分位阈值，切得更碎），而不是按字符硬切。

### 4. 向量维度 2048 硬编码在两处

`ChunkingService.java:36` 与 `EmbeddingService.java:111` 各写了一次 `2048`。换嵌入模型时要同时改两处，漏一处会导致集合维度与实际向量维度不匹配，`upsert` 时报错。

**改进**：提为配置项，或至少收敛到一个常量。

### 5. 文档偏差澄清

`README_Graduation_Defense.md` 中写道「生成诸如 1536 维的浮点数组，落库 Qdrant」。**这与代码不符**，实际维度是 2048（`EmbeddingService.java:111`、`ChunkingService.java:36`）。

以代码为准。

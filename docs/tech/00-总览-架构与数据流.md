## 一、五种存储各自在解决什么

项目同时用了 MySQL、Elasticsearch、Qdrant、Neo4j、Redis。判断这个选择是否合理，关键不在于「用了几种」，而在于**每一种是否都在做 MySQL 做不了的事**。

| 存储 | 承担 | 为什么 MySQL 替代不了 |
| :--- | :--- | :--- |
| **MySQL** | 用户、笔记正文、评论、点赞关系 | —— 它是**唯一的事实来源**，其余四种都是它的派生视图 |
| **Elasticsearch** | 分词倒排索引、相关性打分、高亮 | `LIKE '%关键词%'` 不分词、无法计算相关性得分、无法高亮匹配位置，且前导通配符用不上索引 |
| **Qdrant** | 高维向量的近似最近邻检索 | 2048 维向量的近邻搜索需要专门的索引结构（HNSW 等），SQL 引擎没有这类索引 |
| **Neo4j** | 笔记引用关系的图存储与遍历 | 「两跳之内还连着谁」在 SQL 里是递归自连接，写起来和跑起来都不划算 |
| **Redis** | 浏览量、点赞数等高频计数与缓存 | 高频计数直接落 MySQL 会在热点行上产生锁竞争 |

### 代价必须一起说

多存储不是「亮点」，是**有明确代价的取舍**：

> **五份数据要保持同步。** 一致性问题被从「单库事务」转移到了「跨库同步链路」上——而后者没有事务可用，只能做最终一致。

这正是 [05 篇](05-异步链路与最终一致性.md)的全部主题。那一篇里发现的竞态、丢失的消息、不齐的可靠性等级，全都是这个代价的具体形态。

面试时如果只说「我用了 Polyglot Persistence，根据数据特性选型」，那是背概念；能说出「代价是同步链路，而我的同步链路在这三个地方有问题」才是真的做过。

## 二、一次「保存笔记」发生了什么

```
POST /notes
  │
  ├─ @Transactional 开始                              NoteServiceImpl.java:82
  │    ├─ noteEntryMapper.insert(note) ────────────→  MySQL
  │    ├─ publishEvent(NoteSavedEvent)                :110  ⚠ 事务内发布
  │    └─ 投递 3 条 MQ 任务 SUMMARY / TAG / GRAPH      :114-116  ⚠ 事务内投递
  │
  ├─ 事务提交
  │
  └─ 立即返回用户 ◄── 以下全部尚未完成
       │
       ├─[ Spring 应用事件 · 同进程 ]
       │   ├─ SearchSyncListener ──────────────────→  Elasticsearch  建全文索引
       │   └─ GraphSyncListener  ──────────────────→  Neo4j          解析 [[链接]] 建边
       │        ⚠ @Async @EventListener，可能早于事务提交执行
       │
       └─[ RabbitMQ · 可跨进程，Resilience4j 限流 ]
           └─ AiProcessConsumer
                ├─ SUMMARY ─→ LLM 生成摘要 ────────→  MySQL
                ├─ TAG     ─→ LLM 抽取标签 ────────→  MySQL
                └─ GRAPH   ─→ 构建图谱关系 ────────→  Neo4j
                     ⚠ catch 吞掉所有异常，队列无死信，失败即永久丢失
```

图上三个 ⚠ 是 [05 篇](05-异步链路与最终一致性.md)展开分析的问题。简述：

- **事务内发布**：`@Async` 监听器在另一线程立刻执行，可能在事务提交前回查这条笔记，查不到。MQ 更糟——事务若回滚，消息已经发出去了。
- **AI 任务无兜底**：`AiProcessConsumer` catch 住所有异常只打日志，`ai.process.queue` 也没配死信。

同一个项目里，点赞计数那条链路把这些全都做对了（`@TransactionalEventListener(AFTER_COMMIT)` + 死信队列 + 幂等消息格式）。**正确写法就在同一个代码库里，只是没有回头统一。**

### 向量索引在哪一步

分块 → 嵌入 → 写 Qdrant 这条链路（[01 篇](01-分块策略-从固定长度到语义切分.md)）由 `ChunkingService` 承担。它必须在异步链路里——一篇五千字的笔记要为上百个句子窗口求向量，同步做会让保存操作卡住十几秒。

## 三、Neo4j 与双向链接

这一节是总览独有的内容，也是整套文档里**唯一一处推翻现有项目文档说法**的地方。

### `[[链接]]` 怎么解析

语法借鉴 Obsidian。两个正则（`NoteServiceImpl.java:76-78`）：

```java
private static final Pattern LINK_PATTERN =
        Pattern.compile("\\[\\[([^!][^\\]]*?)\\]\\]");
private static final Pattern CONTENT_LINK_PATTERN =
        Pattern.compile("\\[\\[!article:(\\d+)(?:\\|([^\\]]+))?\\]\\]");
```

第一个匹配笔记间链接 `[[笔记标题]]`，第二个匹配对订阅内容的引用 `[[!article:123]]`。

注意 `LINK_PATTERN` 里的 `[^!]`——它要求第一个字符**不是感叹号**，用来把 `[[!article:...]]` 排除掉，避免两个正则互相误匹配。非贪婪的 `*?` 则保证 `[[A]] 和 [[B]]` 被识别成两个链接而不是一个。

### 出链与反链是两个方向

| | 含义 | 怎么得到 |
| :--- | :--- | :--- |
| **出链**（outgoing） | 这篇笔记引用了谁 | 解析本文的 `[[...]]` 即可 |
| **反链**（backlink） | **谁引用了这篇笔记** | 必须反向查找——扫描所有笔记，看谁的正文里出现了 `[[本文标题]]` |

反链是双向链接的价值所在：写笔记时只需要正向引用，系统自动帮你建立反向索引，于是知识之间自然连成网。

### 关键发现：反链没有走 Neo4j

`README.md` 和 `README_Graduation_Defense.md` 都把双向链接归给了 Neo4j。**代码不是这么做的。**

`NoteServiceImpl.findIncomingLinks()`（`:844`）：

```java
// Find notes containing [[title]]
String searchStr = "[[" + title + "]]";
LambdaQueryWrapper<NoteEntry> wrapper = new LambdaQueryWrapper<NoteEntry>()
        .eq(NoteEntry::getUserId, userId)
        .like(NoteEntry::getContentMd, searchStr);
```

**反链是用 MySQL 的 `LIKE '%[[标题]]%'` 在笔记正文里做子串匹配算出来的**，和 Neo4j 没有关系。

这有两个问题：

1. **性能。** MyBatis-Plus 的 `.like()` 生成前导通配符 `LIKE '%...%'`，**用不上任何索引**。每打开一次笔记详情，就要在该用户的所有笔记正文上做一次全表扫描 + 子串匹配。笔记量大、正文长时，这是详情页最慢的一环。
2. **正确性。** 匹配的是**标题字符串**而不是笔记 ID。改笔记标题，所有指向它的反链会立刻全部失效——因为别人正文里写的还是旧标题。

而 Neo4j 里其实**已经存了这些边**（`GraphServiceImpl.syncNote(note, linkedNoteIds)`），反向遍历一条边正是图数据库最擅长的操作。**能力就在那里，只是详情页没用它。**

### Neo4j 实际用在哪

`GraphServiceImpl`（407 行）对外只有五个方法：

| 方法 | 用途 |
| :--- | :--- |
| `syncNote(note, linkedNoteIds)` | 写入/更新节点与边 |
| `deleteNote(noteId)` | 删除节点 |
| `getGraph(userId)` | 个人图谱可视化取数 |
| `getCommunityGraph(limit)` | 社区图谱可视化取数 |
| `analyzeRelations(userId)` | 关系分析 |

**主体是 Cypher 的增删改查，服务于前端的力导向图渲染。**

需要诚实说明的是：本项目对图数据库的使用**停留在「存关系 + 画出来」，没有用到任何图算法**。Neo4j 真正的能力——PageRank 找出知识网络里的核心节点、社区发现自动做主题聚类、最短路径找出两个概念之间的知识桥接——一个都没用上。

这是 Neo4j 能力远未被用满的地方，也是最明确的改进方向。**不要把它讲成「构建了知识图谱」**——存了节点和边、画了一张力导向图，和「知识图谱」之间还有相当距离。

### 两条贯穿性的观察

汇总起来看，有两个问题不是孤立的：

**其一，失败不可观测是系统性的。** 第 8、9、10、11、12 条全是同一个毛病——降级和失败处理得都对（不阻断用户），但**没有任何机制让自己知道降级发生了**。这个模式在重排、检索、图谱同步三个互不相干的模块里各出现一次，说明它是习惯问题而非偶然疏忽。

**其二，没有评测集导致所有参数都是经验值。** 分块的百分位 85、召回的 20/5、相似度下限 0.5、RRF 的 k=60——没有一个是在本项目数据上调出来的。这不算缺陷，但它意味着**任何参数改动都无法验证好坏**。构造一个几十条问答对的回归集，是提升这条链路的前提。

### 与现有项目文档的四处不一致

写作过程中发现现有文档有四处与代码不符。**以代码为准：**

| 现有文档的说法 | 实际情况 |
| :--- | :--- |
| 支持 OAuth2 (GitHub) 登录 | `security/oauth/` 是**空目录**，`SecurityConfig` 无 `oauth2Login`。认证只有 JWT + 无状态会话 |
| 向量为 1536 维 | 实际 **2048** 维（`EmbeddingService.java:111`、`ChunkingService.java:36`） |
| 双向链接由 Neo4j 支撑 | 反链实际用 MySQL `LIKE` 子串匹配（`NoteServiceImpl.java:844`）；Neo4j 只服务图谱可视化 |
| `SM2Algorithm` 易被读作国密 SM2 | 是 **SuperMemo-2** 间隔重复算法，与密码学无关 |

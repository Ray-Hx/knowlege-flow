# 06 · SuperMemo-2 间隔重复算法

> **先澄清命名。** `common/utils/SM2Algorithm.java` 里的 SM2 指的是 **SuperMemo-2**，一种间隔重复（spaced repetition）算法，**与国密 SM2 椭圆曲线密码算法毫无关系**。本项目没有使用任何国密算法。这个类名很容易被误读，面试时最好主动说明。
>
> 涉及代码：`src/main/java/com/ray/knowledgeflow/common/utils/SM2Algorithm.java`、`module/spaced/service/impl/SpacedServiceImpl.java`（377 行）

---

## 一、这个问题为什么难

用户有 300 条笔记。**今天该复习哪些？**

两个显而易见的答案都不行：

- **全部过一遍**——300 条，不现实。
- **按创建时间轮流**——已经烂熟的内容和刚学的内容占用同样多的复习次数，时间全浪费在不需要复习的东西上。

真正想要的是：**在快要忘掉的那一刻复习**。太早是浪费（本来就还记得），太晚就得重学（已经忘干净了）。

难点在于「快要忘掉」这个时刻**不是一个固定值**：

1. **因材料而异**——一条绕口的定义和一句大白话，遗忘速度差很多。
2. **因人而异**——同一条笔记，不同人的熟悉程度不同。
3. **随复习次数变化**——同一条笔记复习三次之后，遗忘速度会明显变慢。

而系统能观测到的信号只有一个：**用户这次回忆得怎么样**。

所以问题是：**只靠「这次答得好不好」这一个反馈，怎么推断出下次该隔多久？**

## 二、原理

### 遗忘曲线与间隔效应

记忆留存随时间衰减。但关键的实验发现是：**每成功回忆一次，衰减曲线就变平缓一些**，下一次可以隔更久再复习。

```
留存率
 ↑
1├─╮
 │ ╰─╮  第1次复习后          ← 衰减快
 │   ╰──╮
 │      ╰──────╮  第2次复习后 ← 衰减变慢
 │             ╰─────────────╮  第3次复习后 ← 更慢
 └──────────────────────────────────→ 时间
   ↑     ↑            ↑
  复习   复习         复习      ← 间隔逐次拉长
```

这就是间隔递增的依据。剩下的问题是：**递增多少？**

### 两个状态变量

SuperMemo-2 用两个量刻画一条材料的记忆状态：

| 变量 | 含义 | 性质 |
| :--- | :--- | :--- |
| `interval` | 距离下次复习的天数 | **短期状态**，回忆失败时重置 |
| `EF`（easiness factor，难度因子） | 这条材料对这个用户有多容易 | **长期状态**，跨越重置持续累积 |

**这个「长期 / 短期分离」是 SM-2 设计上最精妙的一点**，也是本篇最值得记住的东西。

含义是：即使用户忘了一次、导致间隔清零重新开始，系统**仍然记得「这条材料对你偏难」**，于是重新爬升时会爬得更慢。如果两个变量一起重置，算法就永远学不会「这条对他难」这件事——每次遗忘后都退回「假设它中等难度」，同一个错误会无限重复。

### EF 的递推式

$$
EF' = EF + \bigl(0.1 - (5-q) \times (0.08 + (5-q) \times 0.02)\bigr)
$$

其中 $q$ 是用户的回忆质量评分，取值 0–5。

令 $d = 5 - q$（「差了多少分」），调整量就是：

$$
\Delta = 0.1 - d \times (0.08 + 0.02d) = 0.1 - 0.08d - 0.02d^2
$$

这是一个关于 $d$ 的**二次函数，开口向下**，随 $d$ 增大迅速变负。代入具体数值（下表由 `SM2Algorithm` 的实现逐步复算得出，含 `setScale(2, HALF_UP)`）：

| $q$ | 含义 | 调整量 $\Delta$ | EF 从 2.5 变为 |
| :-: | :--- | :-: | :-: |
| 5 | 完美回忆 | **+0.10** | 2.60 |
| 4 | 略有迟疑 | **0.00** | 2.50 |
| 3 | 勉强想起 | −0.14 | 2.36 |
| 2 | 想不起 | −0.32 | 2.18 |
| 1 | 完全没印象 | −0.54 | 1.96 |
| 0 | 完全遗忘 | **−0.80** | 1.70 |

从这张表能读出两个明确的设计意图：

**1. $q=4$ 是中性点。** 调整量恰好为 0——「答出来了但有点迟疑」既不奖也不惩。**只有完美回忆（$q=5$）才会让 EF 上升。** 算法对「变简单」这件事非常保守。

**2. 惩罚远重于奖励。** 最重的惩罚是 −0.80，最大的奖励只有 +0.10，相差八倍。算法对遗忘高度敏感——**一次彻底遗忘要用八次完美回忆才能抵消**。

### 间隔递推与两个边界

间隔的计算规则：

$$
I(1) = 1 \text{ 天}, \quad I(2) = 6 \text{ 天}, \quad I(n) = I(n-1) \times EF \;\; (n \geq 3)
$$

前两次是**固定的经验值**，不由 EF 决定；从第三次起才进入指数增长，增长率就是 EF。

两个边界条件是本篇的考点所在：

**边界 1：EF 下限 1.3。**

这是为了防止指数增长退化成常数。如果 EF 能降到 1.0，那么 $I(n) = I(n-1) \times 1.0 = I(n-1)$——**间隔永远不再增长**，用户会被这条难材料无限纠缠，每次都隔同样的天数复习。EF 若低于 1，间隔甚至会**缩短**，越复习越频繁。

1.3 保证了最难的材料间隔也仍在增长，只是很慢（每次乘 1.3）。

实测这个下限多久会触发：从 2.5 出发，**连续两次 $q=0$ 就会触底**（2.5 → 1.70 → 1.30）。

**边界 2：$q < 3$ 时重置。**

回忆失败（$q$ 为 0、1、2）说明前面积累的间隔判断错了，于是 `repetitionCount` 归零、间隔退回 1 天，从头再爬。

**但 EF 不重置**——这正是前面「长期 / 短期分离」的落点。

## 三、代码走读

### 四个常量

`SM2Algorithm.java:35-50`：

```java
private static final BigDecimal MIN_EF = new BigDecimal("1.3");
private static final BigDecimal INITIAL_EF = new BigDecimal("2.5");
private static final int FIRST_INTERVAL = 1;
private static final int SECOND_INTERVAL = 6;
```

与第二节一一对应。注意 `BigDecimal` 用的是**字符串构造器** `new BigDecimal("1.3")` 而不是 `new BigDecimal(1.3)`——后者接收 double，会把 1.3 的二进制浮点误差原样带进 BigDecimal，得到 `1.3000000000000000444089209850062616169452667236328125`。这是 `BigDecimal` 最常见的误用。

### 主流程：注意执行顺序

`SM2Algorithm.java:61`：

```java
public static SM2Result calculate(int quality, int repetitionCount,
        int intervalDays, BigDecimal easinessFactor) {
    // 验证输入参数
    if (quality < 0 || quality > 5) {
        throw new IllegalArgumentException("质量评分必须在0-5之间");
    }

    SM2Result result = new SM2Result();

    // 计算新的难度因子 (EF)
    BigDecimal newEF = calculateEasinessFactor(quality, easinessFactor);   // :72
    result.setNewEasinessFactor(newEF);

    // 质量评分 < 3 时，重置学习进度
    if (quality < 3) {                                                      // :76
        result.setNewRepetitionCount(0);
        result.setNewIntervalDays(FIRST_INTERVAL);
    } else {
        int newRepetitionCount = repetitionCount + 1;
        result.setNewRepetitionCount(newRepetitionCount);
        int newIntervalDays = calculateInterval(newRepetitionCount, intervalDays, newEF);  // :85
        result.setNewIntervalDays(newIntervalDays);
    }

    result.setNextReviewTime(LocalDateTime.now().plusDays(result.getNewIntervalDays()));   // :90
    return result;
}
```

**执行顺序是这段代码最重要的信息：`calculateEasinessFactor` 在 `:72` 调用，而 `quality < 3` 的判断在 `:76`。**

也就是说——**EF 的更新发生在重置判断之前，因此评分再低，EF 也照样更新。** 这正是第二节「EF 不重置」在代码上的体现。

这个顺序很容易被实现错。一个自然但错误的写法是：

```java
if (quality < 3) {
    // 忘了，全部重置
    result.setNewRepetitionCount(0);
    result.setNewIntervalDays(FIRST_INTERVAL);
    result.setNewEasinessFactor(INITIAL_EF);   // ← 错：把 EF 也重置了
} else { ... }
```

这样写，算法就丧失了「记住这条材料对你难」的能力。**当前实现是对的**，值得在面试时指出来。

另外注意 `:85` 传给 `calculateInterval` 的是 **`newEF`**（刚算出来的），不是旧 EF——本次评分立即影响本次间隔，而不是下次才生效。

### EF 计算

`SM2Algorithm.java:102`：

```java
private static BigDecimal calculateEasinessFactor(int quality, BigDecimal currentEF) {
    // EF' = EF + (0.1 - (5-q)*(0.08+(5-q)*0.02))
    int diff = 5 - quality;

    BigDecimal factor1 = new BigDecimal("0.08");
    BigDecimal factor2 = new BigDecimal("0.02").multiply(new BigDecimal(diff));
    BigDecimal factor3 = factor1.add(factor2).multiply(new BigDecimal(diff));
    BigDecimal adjustment = new BigDecimal("0.1").subtract(factor3);

    BigDecimal newEF = currentEF.add(adjustment);

    // 确保 EF >= 1.3
    if (newEF.compareTo(MIN_EF) < 0) {
        newEF = MIN_EF;
    }

    return newEF.setScale(2, RoundingMode.HALF_UP);
}
```

**为什么全程用 `BigDecimal` 而不是 `double`？**

不是因为「金额才用 BigDecimal」这种教条，而是有具体理由：

1. **EF 是跨次累积的状态。** 每次复习都在上一次的结果上继续加减，误差会随复习次数累积，而不是每次独立计算。
2. **EF 直接乘进间隔天数** ($I(n) = I(n-1) \times EF$)，误差最终会体现为**复习日期的偏移**。
3. **`setScale(2, HALF_UP)` 让状态可精确复现。** EF 固定两位小数存进数据库，读出来再算，结果与上次完全一致。用 double 存取则可能出现 `2.5999999999999996` 这类值，且不同的运算顺序可能给出不同结果。

对比一下：如果用 double，`0.1 - 3 * (0.08 + 0.02 * 3)` 算出来是 `-0.31999999999999995` 而不是 `-0.32`。单次无害，累积几十次并参与乘法后就未必了。

### 间隔计算

`SM2Algorithm.java:129`：

```java
private static int calculateInterval(int repetitionCount, int currentInterval,
        BigDecimal easinessFactor) {
    if (repetitionCount == 1) {
        return FIRST_INTERVAL;
    } else if (repetitionCount == 2) {
        return SECOND_INTERVAL;
    } else {
        // I(n) = I(n-1) * EF
        BigDecimal newInterval = new BigDecimal(currentInterval).multiply(easinessFactor);
        return newInterval.setScale(0, RoundingMode.HALF_UP).intValue();
    }
}
```

三分支对应第二节的递推式。`setScale(0, HALF_UP)` 把天数取整——间隔是以「天」为粒度的，不需要小数。

### 初始状态里的一个小技巧

`SM2Algorithm.java:147`：

```java
public static SM2Result getInitialState() {
    SM2Result result = new SM2Result();
    result.setNewRepetitionCount(0);
    result.setNewIntervalDays(0);
    result.setNewEasinessFactor(INITIAL_EF);
    // 设置为1分钟前，确保初始化后立即可被复习
    result.setNextReviewTime(LocalDateTime.now().minusMinutes(1));
    return result;
}
```

`nextReviewTime` 设成**一分钟前**而不是「现在」。

原因是查询到期卡片的条件通常是 `where next_review_time <= now()`。如果设成 `now()`，那么这条记录能否立刻被查到，就取决于「写入的那一刻」和「查询的那一刻」之间的微小时间差，以及数据库时间戳的精度（有的只到秒）。设成一分钟前，条件必然成立，**把一个边界相等问题变成了明确的不等**。

小技巧，但很能说明写代码时对边界条件的敏感度。

### 调用方

`SpacedServiceImpl.java:112` 提交复习结果：

```java

                dto.getQuality(), ...);
```

## 四、为什么不用更现代的算法

| 方案 | 取舍 |
| :--- | :--- |
| **固定间隔**（1/3/7/15/30 天） | 实现最简单。但对所有材料一视同仁——学得快的被反复打扰，学不会的又跟不上。第一节否定的就是它 |
| **SuperMemo-2**（本项目） | 两个状态变量、纯函数、无需任何训练数据，冷启动即可用，几十行实现完，且完全可解释——能对用户说清「为什么下次是 15 天后」 |
| **SM-17 / SM-18** | SuperMemo 的后续版本，引入更完整的记忆模型（含难度、稳定性、可提取性三个维度），精度更高。代价是复杂度大幅上升，且部分版本并非完全公开 |
| **FSRS** | 当前主流，Anki 已默认采用。基于大规模真实复习数据拟合的记忆模型，效果明显优于 SM-2。**代价是需要参数和训练数据**——个人项目冷启动阶段一条复习记录都没有，没有东西可拟合 |

### 诚实的结论

**SM-2 是 1987 年的算法，已经不是当前最优。** FSRS 在公开对比中表现更好，这是事实。

选 SM-2 的理由是**零数据依赖**：项目刚上线时没有任何复习记录，FSRS 无从拟合参数，而 SM-2 开箱即用。等积累了足够多的真实复习数据之后，迁移到 FSRS 是合理的演进方向。

面试时这样说，比硬夸 SM-2 先进要好得多——**知道自己用的东西的时代局限，本身就是一种技术判断力。**

## 五、追问预演

### 第一层：EF 的下限为什么是 1.3？

讲第二节边界 1 的逻辑：EF 是间隔的增长率，低于 1 间隔就不增长甚至缩短，用户会被难材料锁死。1.3 保证最难的材料间隔也仍在增长，只是慢。

这个值来自 SuperMemo 原始论文给出的经验下限。可以补一个实测数据：从初始 2.5 出发，**连续两次 $q=0$ 就会触底**。

### 第二层：$q < 3$ 时你把 repetitionCount 和 interval 都重置了，但 EF 没重置。为什么不一起重置？

**这是本篇的核心考点。**

讲长期 / 短期状态分离：

- `interval` 反映「当前这一轮爬到哪了」。回忆失败说明这一轮的间隔判断错了，该重爬。
- `EF` 反映「这条材料对你有多难」。回忆失败恰恰**印证**了「这条材料难」这个判断，这个认知是正确的，应当保留。

保留 EF 的效果是：重爬时爬得更慢（因为 EF 已经被降低了），符合「这条对你难，就多复习几次」的直觉。

**如果连 EF 一起重置**，用户每次遗忘都会回到「假设这条材料中等难度」，算法**永远学不会**这条材料对他而言很难——同一个错误会无限重复。

代码上这一点体现为执行顺序：`calculateEasinessFactor` 在 `:72`，早于 `:76` 的 `quality < 3` 判断。

### 第三层：`nextReviewTime` 是 `LocalDateTime.now().plusDays(interval)`。假设一张卡片本该 7 月 1 日复习，用户 7 月 10 日才打开，答对了，你算出下次间隔 15 天，下次复习日就是 7 月 25 日。但从「上次复习日」算本该是 7 月 16 日。迟到的 9 天你完全没处理——这会怎么样？

**这是真实缺陷，当前实现确实没有处理。** 两个后果：

**后果 1：复习计划随用户的拖延持续后移。** 每次迟到都会把后续所有日程往后推，间隔在无意中被拉长。用户越拖，系统越纵容。

**后果 2（更本质）：丢失了一个重要信号。** 用户隔了 16 天还能答对，说明这条材料**比 EF 记录的更容易**——这是一条有价值的信息。标准 SM-2 之后的改进版本（包括 FSRS）会把「实际间隔 vs 计划间隔」的比值纳入难度估计，本实现完全没有利用。

**顺带还有一个时区问题**：`LocalDateTime.now()` 取的是**服务器本地时区**。用户在另一个时区时，「今天该复习什么」的判断会错位——服务器的 7 月 22 日 0 点，对用户可能还是 7 月 21 日下午。

**改进方向**：下次时间从**计划到期日**而非 `now()` 推算；存储用 `Instant` 或 UTC，展示时按用户时区转换。

## 六、现有实现的坑与改进方向

### 1. 迟到复习未处理

`SM2Algorithm.java:90`：

```java
result.setNextReviewTime(LocalDateTime.now().plusDays(result.getNewIntervalDays()));
```

从 `now()` 推算，而非从计划到期日推算。且实际间隔未反馈进 EF。见第五节第三层。

### 2. `LocalDateTime.now()` 依赖服务器时区

同样在 `:90` 和 `:153`。跨时区用户的到期判断会错位。

**改进**：改用 `Instant` / UTC 存储，展示层按用户时区转换。

### 3. `now()` 写死在算法内部，无法做确定性单元测试

`calculate()` 是个纯函数——**除了 `:90` 这一行**。因为它直接调 `LocalDateTime.now()`，导致「下次复习时间」这个输出无法被断言：测试写不出 `assertEquals(expectedTime, result.getNextReviewTime())`，只能断言天数。

**改进**：把 `Clock` 作为参数传入（`Clock.systemUTC()` 生产用，`Clock.fixed(...)` 测试用）。这是 Java 8 时间 API 专门为可测试性设计的机制。

### 4. 重置后的间隔与初始状态不一致

两条「从头开始」的路径给出了不同的初始间隔：

| 路径 | `repetitionCount` | `intervalDays` |
| :--- | :-: | :-: |
| `getInitialState()`（`:147`，新卡片） | 0 | **0** |
| `quality < 3` 重置（`:76`） | 0 | **1**（`FIRST_INTERVAL`） |

同样是「回到起点」，一个 0 一个 1。实际影响不大（因为下次成功复习时 `repetitionCount` 变成 1，走 `FIRST_INTERVAL` 分支，都会得到 1 天），但两条路径的语义应当统一，否则读代码的人会疑惑哪个才是「起点」。

### 5. `quality` 用裸 `int`，靠运行时抛异常校验

`:64` 用 `if (quality < 0 || quality > 5) throw new IllegalArgumentException(...)` 做校验。

问题是**编译期挡不住**任何东西——调用方传 7 要等到运行时才炸。而前端实际上只有几个按钮（「简单 / 中等 / 困难」之类），根本不是连续的 0–5 取值。

**改进**：用枚举表达实际的评分档位，既在编译期收口，也让代码更贴近真实的交互模型。

### 6. 算法本身已被 FSRS 超越

见第四节。当前是合理选择（零数据依赖），但如果项目积累了足够的真实复习记录，迁移到 FSRS 是明确的演进方向。

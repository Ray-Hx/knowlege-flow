## 1. 目标与非目标

### 目标

产出一套 **深度优先** 的技术文档，服务两个场景：

1. **自己复盘**——隔了几个月回看，能重新建立起对每个技术决策的完整理解。
2. **面试讲解**——面对面试官逐层追问时，有推导过程、有选型对比、有对自身实现局限的清醒认识。

衡量标准：**任意一篇文档，读完后能独立支撑 30 分钟的深度追问。**

### 非目标

- 不是「跟着做能跑起来」的复刻教程，不写环境搭建、依赖安装、启动步骤（`README.md` 已覆盖）。
- 不是 API 手册，不逐个罗列接口签名。
- 不追求模块全覆盖。宁可 6 篇写透，不要 9 篇泛泛而谈。

### 与现有文档的关系

仓库已有三份文档，都是**介绍性**的——罗列用了什么技术，不解释为什么这么选、怎么实现：

| 文件 | 定位 | 本次是否改动 |
| :--- | :--- | :--- |
| `README.md` | 功能特性 + 快速开始，面向使用者 | 不改，仅在末尾加一行指向 `docs/tech/` |
| `TECHNICAL_DETAILS.md` | 模块清单，每模块 3-5 条要点 | 不改 |
| `README_Graduation_Defense.md` | 答辩叙事 | 不改 |

新文档是**增量补充**，填补「为什么」和「怎么实现」这一层，不重写也不替换以上三份。

## 2. 已发现的文档与代码不一致

写作时必须以**代码为准**，以下三处现有文档存在偏差，新文档不得沿用：

1. **OAuth2 GitHub 登录未实现。** `README.md` 与 `README_Graduation_Defense.md` 均宣称支持，但 `src/main/java/com/ray/knowledgeflow/security/oauth/` 是空目录，`SecurityConfig` 中也无 `oauth2Login` 配置。认证实际只有 JWT + 无状态会话。
2. **`common/utils/SM2Algorithm.java` 是 SuperMemo-2 间隔重复算法，不是国密 SM2 加密。** 命名容易误读，文档中必须写全称 SuperMemo-2 并明确澄清。
3. **向量维度是 2048，不是 1536。** `README_Graduation_Defense.md` 称「生成诸如 1536 维的浮点数组」，实际 `EmbeddingService.java:111` 与 `ChunkingService.java:36` 均使用 2048。
4. **代码能力强于文档描述。** 现有文档只说「Qdrant 向量检索」，实际实现了语义分块（分位数阈值）、召回-精排两段式、三种可插拔重排器、自建本地重排推理服务。这些是本次文档的主要素材来源。

## 4. 统一模板

每篇文档遵循同一六段式结构。段落标题保持一致，便于横向对比和快速定位。

### ① 这个问题为什么难

从**具体的失败场景**切入，而不是从技术名词切入。

> 反例：「本项目采用语义分块技术。」
> 正例：「一段讲 RRF 的论述被从中间截断，前半段留在 chunk A，后半段进了 chunk B。用户问『RRF 的 k 取多少』，检索命中 chunk A，但 k 的取值在 chunk B 里——检索『成功』了，答案却是错的。」

### ② 原理

从零推导，不假设读者知道该技术。公式必须解释**每个符号的含义和量纲**，并说明**为什么是这个形式**。

以 RRF 为例，不能只写 `score = Σ 1/(k + rank)`，要回答：为什么用排名不用分数；为什么是倒数；k 在里面起什么作用；k 趋近 0 和趋近无穷时分别退化成什么。

### ③ 代码走读

**粒度：关键片段 + 行号锚点。**

- 只贴能说明原理的 10-30 行核心片段。
- 其余用 `SearchServiceImpl.java:511-540` 形式指路，不整段复制。
- 每个片段前先说明「这段在解决 ① 里的哪个问题」。
- 行号必须与当前代码一致，写作时逐一核对。

理由：整段贴代码会让文档臃肿，且代码一改文档就大面积失真；行号锚点即使漂移，附近上下文也足以定位。

### ④ 为什么不用 X 而用 Y

列出当时**真实考虑过或应当考虑的**备选方案，给出取舍理由，并诚实标注哪些是事后补充的分析。

不允许编造「我当时对比了五种方案」这类不实叙述——面试官追问细节时会露馅。

### ⑤ 追问预演

按面试官**往下钻三层**的方式组织，而不是罗列独立问答。

示例（04 篇）：

- 第一层：为什么 RRF 常数取 60？
- 第二层：改成 10 会发生什么？
- 第三层：ES 的 BM25 分数和向量余弦相似度量纲完全不同，你确定排名融合能规避这个问题吗？边界情况呢？

每层给出可直接说出口的回答，标注哪些地方**不能硬撑**、应当直接承认不确定。

### ⑥ 现有实现的坑与改进方向

**这一段是文档可信度的关键。** 主动指出自己实现里的问题，比掩盖它们更有说服力。

已核实的真实问题（写作时须再次确认行号）：

- **RRF 常数硬编码两处。** `SearchServiceImpl.java:366` 与 `:511` 各写了一次 `k = 60`，应提为配置项。
- **两个分页 total 都不准，但成因不同。** `searchContentSemantic` 用 `resultList.size()`（仅当页条数）作 total，代码注释已承认 Qdrant 不易获取精确 total；`searchContentHybrid` 用 `sortedIds.size()`（融合候选数）作 total，因此 total 被 `candidateSize` 封顶，不是语料库真实命中数。**这两处不可混为一谈。**
- **ES 分支静默降级。** `searchContentHybrid` 的 ES 任务 catch 后返回空列表，ES 故障时混合检索会无声退化为纯向量检索，调用方无法感知。
- **AI 队列没有重试与死信。** `AiProcessConsumer.handleAiProcessTask` catch 住所有异常仅打日志，源码里留有 `// TODO: 可以考虑重试机制或发送到死信队列`。与之对照，`engagement.sync.queue` 配置了 DLX。同一个项目里两种可靠性等级并存，是 05 篇的核心对照素材。
- **事务提交前发布事件与消息。** `NoteServiceImpl.createNote` 标注 `@Transactional`（:82），却在事务内的 :110 发布 `NoteSavedEvent`、:114-116 投递 MQ 任务。`GraphSyncListener` 用 `@Async @EventListener` 立即在另一线程执行，可能在事务提交前回查该笔记。经典的「提交前发布」竞态，应改用 `@TransactionalEventListener(phase = AFTER_COMMIT)`。
- **`SemanticChunker` 无嵌入缓存。** 每次分块要为每个句子窗口求一次向量，长文档嵌入调用开销显著。
- **`syncAll` 先 `deleteAll()` 再逐条 `save()`。** 全量同步期间索引处于空/半空状态，且未使用批量 API。

## 5. 写作准则

1. **代码为准。** 任何论断必须能在代码中找到依据。与现有文档冲突时以代码为准，并在文中明确指出偏差（见第 2 节）。
2. **不美化。** 不使用「颠覆性」「极致」「业界领先」这类词。技术文档的说服力来自准确，不来自形容词。
3. **不编造数据。** 未实测的性能数字一律不写。要写必须标注来源，或明确写「未实测」。
4. **中文为主。** 技术专有名词首次出现时中英并列，如「交叉编码器（cross-encoder）」，其后统一用一种写法。
5. **行号必须核对。** 每个 `file:line` 引用在写作时实际打开确认。
